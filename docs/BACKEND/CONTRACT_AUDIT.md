# 백엔드 ↔ Android·iOS 계약 점검 (2026-10-12)

이 문서는 **점검 시점(2026-10-12)의 현황 기록**이다. §6의 질문은 모두 답을 받았고, 결정된 계약은 `docs/BACKEND/CONTRACT_DECISIONS.md`에 API 단위로 기록했다. 이 문서의 "권장"과 결정이 다르면 결정 문서가 우선한다.
이번 점검에서는 코드와 기존 설계 문서를 수정하지 않았다. 구현 여부는 문서의 상태 표기가 아니라 실제 코드(`src/main/java`, `ios/HAWE`, `android/app/src/main`)를 보고 판정했다.

## 0. 전제 — 먼저 알아야 할 사실

1. **두 앱 모두 네트워크 계층이 없다.** HTTP 클라이언트, 토큰 저장, `/api` 호출 코드가 전혀 없다. 모든 화면이 앱 안의 메모리 저장소(`DataStore`)를 읽고 쓰며, 앱을 종료하면 데이터가 사라진다. 따라서 이 문서의 "앱 현재 상태"는 호출 코드가 아니라 **데이터 모델과 화면 동작**을 기준으로 적었다. (`ios/HAWE/Core/Data/DataStore.swift`, `android/.../core/data/DataStore.kt` — "서버를 붙일 때는 이 클래스의 공개 메서드 안쪽만 API 호출로 바꾸면 돼요")
2. **Android는 iOS를 1:1로 옮긴 앱이다.** 모델, `DataStore` 공개 메서드, 화면 규칙이 같다. 계약에 영향을 주는 차이는 없고 사소한 차이만 §5에 적었다.
3. **앱과 백엔드가 서로 다른 제품 규칙을 기준으로 만들어졌다.** 앱은 iOS 쪽 자체 기획(코드 주석의 `CLAUDE.md §1~§7`, Supabase·RLS를 가정한 흔적: `ios/Config.example.xcconfig`의 `SUPABASE_URL`, `DataStore.result`의 "서버에서는 RLS 로 막아요")을 따른다. 백엔드는 `docs/FEATURE/PROJECT_OVERVIEW.md`와 `MISSIONS_API.md`를 따른다. 핵심 차이:

| 영역 | 백엔드(코드·설계) | 앱(iOS·Android 공통) |
|---|---|---|
| 로그인 | 아이디(`loginId`)/비밀번호 자체 가입, 소셜 로그인은 MVP 제외 | 이메일/비밀번호 + Apple·카카오·Google 간편 로그인, 계정 연결/해제 |
| 미션 | 하루 N개(1~5) 슬롯, 21종 틀 중 16종을 1차로 구현(사진/음성/글/그림/**슬라이더**), 틀마다 `params`와 제출 형식이 다름 | 하루 1개, 유형 4종(그림/사진/글/음성) + 자유 주제 문장 1줄 |
| 미션 시간 | 슬롯별 발행·마감 시각, 마감 뒤 제출은 `isLate` | 주제 도착 시각부터 다음 날 같은 시각까지 24시간, 지각 개념 없음 |
| 초대 | 그룹장만 발급, 7일 만료 JWT 딥링크 `hawe://join?token=` | 그룹마다 영구 6자리 코드, 멤버 누구나 복사·공유, `https://hawe.app/invite/{code}` |
| 그룹장 나가기 | 금지 (`OWNER_CANNOT_LEAVE`) | 가장 먼저 들어온 멤버에게 그룹장이 넘어감 |
| 정원 | 없음 | 연인 2명, 그 외 6명 |
| 반응 | 스티커 토글(`stickerType`) | 하트 좋아요 1종 + 누른 사람 이름 |
| 달력 | 마이페이지 통합 달력, 도장(참잘했어요/벌점) | 그룹별 달력, 유형·주제·참여 수 표시, 도장/벌점 없음 |
| 알림 | 알림 목록 API(설계) | 알림 목록 화면 없음. 푸시 4종 + 알림 설정 + 그룹별 알림 켜기/끄기 |
| 프로필 | 계정 1개 캐릭터 | 기본 프로필(캐릭터 또는 사진 + 닉네임) + **그룹마다 다른 프로필** |

이 차이는 개별 필드를 맞추는 것만으로는 해결되지 않는다. 영역마다 어느 쪽 규칙을 따를지 먼저 정해야 한다 (§6 질문).

## 4. 미구현 API — 설계 문서 vs 앱이 기대하는 동작

코드가 없으므로 "구현된 것처럼" 비교하지 않고, **설계 문서와 앱 화면** 사이의 차이만 적는다.

### 4-1. 설계가 있는 API

| 영역 | 설계 (문서) | 앱이 기대하는 동작 | 차이 | 결정 |
|---|---|---|---|---|
| 제출 `POST /missions/{id}/submissions` | multipart, 틀별 필드(`file/text/number/guess/choice/answer/alias/caption`), 음성 ≤ 20초, 이미지 jpg/png/webp ≤ 10MB, 1인 1회, 지각 허용 | 그림 PNG, 사진 JPEG, 글, 음성 m4a **최대 30초** + 길이 + **파형 배열**. 1회 제출, 수정·삭제 불가. 캡션 없음 | 음성 길이(20 vs 30초), 파형을 서버가 저장할지(설계에 없음), 30초 스케치 타이머(설계는 클라이언트 강제, 앱 그림 화면엔 타이머 없음) | Q-M1, Q-S1 |
| 피드 `GET /missions/{id}/submissions` | 내가 제출해야 열림(423 `FEED_LOCKED`), 항목: 작성자 nickname, `reactionCount`, `commentCount` | 내가 올린 미션만 결과 공개 — **같은 규칙**. 항목: 작성자 아바타(그룹 내 프로필), 좋아요 수·내가 눌렀는지·누른 사람 이름, 댓글 목록, **아직 안 낸 멤버 목록**, 전체 인원 | 응답 필드 부족(아바타, `likedByMe`, 미제출 멤버) | Q-R1 |
| 게시물 상세 `GET /submissions/{id}` | 반응 종류별 수, 댓글 수 | 좋아요 토글 + 댓글 목록 + 입력 | 반응 모델 차이 | Q-R1 |

| 정답 맞히기, 집계 결과 | 설계 있음 | 화면 없음 | Q-M1 결과에 따름 | Q-M1 |
| 알림 `GET /notifications`, 읽음 처리 | 알림 목록 + 읽음 | 알림 목록 화면 없음. 푸시 종류 `topic/poke/friend_done/comment`, payload `type/group_id/submission_id` | 설계 알림 종류(`poke`, `mission_open`)와 앱 푸시 종류가 다름. 목록 API를 MVP에 둘지 | Q-N1 |
| 달력 `GET /me/calendar` | 마이페이지 통합 달력, 날짜별 도장 `GOOD/PENALTY`, 날짜 상세 | 15 화면: **그룹별** 월 달력, 날짜마다 유형·주제·참여 수/인원·내 제출 여부, 누르면 결과 공개. 도장·벌점 표현 없음 | 범위(통합 vs 그룹별)와 도장 개념 | Q-C1 |

## 5. Android ↔ iOS 차이

계약에 영향을 주는 차이는 없다. 서버 연결 때 함께 고치면 좋은 사소한 차이만 적는다.

| 항목 | Android | iOS | 권장 |
|---|---|---|---|
| 그룹 만들기·나가기 중복 탭 방지 | 있음 (`submitted`, `leaving` 플래그) | 없음 | iOS도 막기 — 서버 연결 후 중복 `POST /groups`가 나갈 수 있음 |
| 관계 장식(가족·그저그런사이) | 벡터 이미지 | SF Symbol 임시 표시 | 디자인 문제, 계약과 무관 |

| 푸시 처리 | 9단계 구현(채널 4종, 디버그 수신기) | `PushNotifications.swift` | 동작 같음 (payload `type/group_id/submission_id`) |
