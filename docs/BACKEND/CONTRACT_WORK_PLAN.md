# 계약 반영 작업 순서

`docs/BACKEND/CONTRACT_DECISIONS.md`에서 결정한 계약을 코드와 설계 문서에 반영하는 순서다. 현황은 `CONTRACT_AUDIT.md`, 결정은 `CONTRACT_DECISIONS.md`(절 번호 §는 그 문서 기준)를 본다. 이 문서는 2026-10-12에 작성했다.

## 1차 범위 (우선 구현) — 로그인 / 그룹 / 미션 수행

시간이 부족해 **가입 → 그룹 → 오늘 미션 제출 → 결과 확인**까지만 먼저 서버로 연결한다. 나머지는 2차로 미룬다. 푸시는 FCM(Firebase)으로 하기로 했고(결정 문서 §8) 2차에서 진행한다.

| 단계 | 1차에 하는 것 | 2차로 미루는 것 |
|---|---|---|
| 1 공통 | 시간대 Asia/Seoul 고정, 오프셋 시각, 404/400/405 처리기 | — |
| 2 Auth | 이메일 가입·로그인·refresh, `GET /me`, 앱 네트워크 계층·토큰 저장소, 닉네임·약관 검증 | `PATCH /me/password`(17-2는 "준비 중"), 간편 로그인·비밀번호 찾기("준비 중" 안내는 1차에 포함) |
| 3 Group | 생성(`startDate` 포함), 목록, 상세, 6자리 코드 미리보기·참여, 정원, 일반 멤버 나가기, 멤버 목록 | 초대 코드 재발급, 설정 변경(주제 도착 시각은 기본 09:00 고정), 그룹장 나가기(후임자 선택, 서버는 `SUCCESSOR_REQUIRED` 반환·앱은 "준비 중" 안내), 그룹 내 프로필, 그룹별 알림 |
| 4 미션 | 고정 문장 임시 생성기, MVP 틀 8종, 첫 미션 즉시 발행, 마감·지각·제출 종료 규칙, 현재 미션 조회, 홈 카드의 `todayMission` | AI 연동, 하루 여러 개, 틀 선택 규칙의 세부 |
| 6 제출·피드 | 제출(사진·그림·글·음성, 파일은 로컬 저장), 피드·상세(잠금 규칙), 결과 화면 연결 | 파형 정확도 개선 등 |

1차에서 서버에 아직 없는 기능의 앱 화면 처리: 콕 찌르기·똥뿌리기 버튼, 스티커·댓글 입력, 달력의 도장, 마이페이지 활동 요약은 **숨기거나 "준비 중"** 으로 두고 목업 데이터로 동작시키지 않는다 (서버 데이터와 섞이지 않게).

2차로 미루는 단계: 5 콕, 7 반응·댓글, 8 Me 나머지(프로필 사진·탈퇴), 9 알림(FCM), 10 달력. 이 순서와 내용은 아래 표 그대로다.

## 진행 방식

- 각 단계는 **설계 문서 → 백엔드(테스트·Postman 포함) → Android·iOS** 순서로 한 묶음이다. 문서를 한꺼번에 먼저 고치면 코드와 다시 어긋나기 쉬우므로 해당 API의 문서만 그 단계에서 고친다.
- 백엔드는 앱보다 한 단계 앞서 가도 된다 (앱이 2단계를 연결하는 동안 백엔드는 3단계).
- 마이그레이션은 단계마다 하나씩 V6, V7… 순서로 만든다. 2·3단계는 개발 DB 데이터 정리(초기화 여부)를 그 시점에 정한다.
- **3단계와 4단계는 동시에 진행하지 않는다.** 둘 다 `GroupService`, `GroupMapper`, 그룹 응답을 수정한다.
- 첫 목표는 1~4단계: 가입 → 그룹 만들기·초대 → 오늘 미션 확인이 실제 서버로 동작하는 것.
