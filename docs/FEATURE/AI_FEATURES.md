# AI 신규 기능 설계 (초안)

작성: 2026-11-09. 상태: **설계 초안 — 구현 전.** 신규 기능 6~7개 중 AI 쪽 4개를 먼저 정리한다. 나머지 기능은 별도 문서로 추가한다.
구현 계획(`.agent/plan.md` 형식)은 이 문서의 열린 결정(§6)이 정해진 뒤 기능별로 쪼개서 만든다.

| # | 기능 | 한 줄 요약 | 실행 위치 | 서버 변경 | 기존 자산 재사용 |
|---|---|---|---|---|---|
| 1 | 실시간 AI 판단 | 그리는 도중 AI 가 계속 추측하고, 맞히는 순간 반응 | 기기 | 없음 | M1 모델·A8 전처리 |
| 2 | AI 미션 검색 | 키워드와 관련된 지난 미션을 의미 기반으로 찾기 | 서버 | 검색 API 1개 + 색인 | B8 LLM 클라이언트, B11 Nori |
| 3 | 얼굴 자동 블러 | 사진의 얼굴을 찾아 골라서 모자이크 | 기기 | 없음 | — |
| 4 | 멀티 암드 밴딧 | 그룹별로 참여가 잘 나오는 틀을 학습해 더 자주 발행 | 서버 | 틀 선택기 + 통계 테이블 | `MissionTemplateSelector`, B9 지표 |

## 0. 공통 원칙 (기존 결정과의 정합)

이미 확정된 원칙을 새 기능이 깨지 않도록 먼저 못 박는다.

1. **기기 안 처리 우선.** 그림(M1/A8)은 서버로 보내지 않는다. 1·3번은 같은 방식을 따른다.
2. **LLM/외부 AI 에 사용자 콘텐츠를 보내지 않는다.** (`B8` 결정 #11: 미션 단위 집계만, 사용자 글·댓글·사진·닉네임·그룹 이름 금지.) 2번 검색은 이 때문에 **미션 문장(서버가 만든 문장)** 만 대상으로 한다. 사용자 제출물(글·캡션)은 색인하지 않는다.
3. **잠금 규칙.** 내가 제출하지 않은 미션의 피드는 볼 수 없다(`423`). 검색이 이 규칙을 우회하는 통로가 되면 안 된다.
4. **틀 선택 규칙 2·3(매체 순환·어제 매체 제외)은 필수 제약**이고 **규칙 4(관계별 선호·가중치 없음)는 확정**이다(`MISSIONS_API.md` §6-1). 4번 밴딧은 이 둘 안에서만 동작한다 — §4.6 참조.
5. **AI 는 제출을 평가·점수화하지 않는다.** 1번은 "재미용 추측"이고 제출·도장·점수에 영향을 주지 않는다(A8 제약 그대로).
6. 디자인(Figma)이 없는 UI 는 임시 에셋으로 채우고 `임시` 주석을 단다.

## 1. 실시간 AI 판단 (Quick, Draw! 방식)

### 1.1 현재와 달라지는 점

| | 지금 (M1 + A8, 완료) | 이 기능 |
|---|---|---|
| 시점 | 그림을 다 그린 뒤 "AI에게 보여주기" 버튼 → 1회 추론 | **획을 그을 때마다** 연속 추론 |
| 연출 | 결과 카드 | "AI 가 지켜보는 중" 말풍선이 실시간으로 바뀌고, **맞히는 순간 즉시 반응** |
| 게임성 | 보기 전용 | 30초 스케치(`DRAW_SKETCH`)와 결합 — "AI 가 몇 초 만에 맞혔나" |
| 모델 | `quickdraw_cnn.tflite` (28×28, ~50범주) | **같은 모델 재사용** (재학습 불필요) |

즉 새 모델이나 서버가 필요 없고, **추론 호출 빈도·안정화·UI** 의 문제다. 모델은 28×28 입력 소형 CNN(목표 ≤30 ms)이라 획마다 호출해도 부담이 작다.

### 1.2 동작

1. 캔버스에서 **획이 끝날 때(pointer up)** + 그리는 중에는 **500 ms 디바운스**로 `InkPreprocessor → QuickDrawClassifier` 실행. (그리는 도중 매 프레임 호출하지 않는다.)
2. 추론은 백그라운드 디스패처, 이전 추론이 끝나기 전 새 요청은 최신 것만 남기고 버린다(coalescing).
3. **안정화**: 상위 1위가 흔들리면 말풍선이 깜빡이므로, 최근 3회 확률의 지수이동평균으로 표시. 1위가 바뀌려면 새 1위가 기존 1위보다 `+0.1` 이상 높아야 한다(히스테리시스).
4. **맞힘 판정**: 미션 주제가 범주에 매핑되고(`DrawSubjectMatcher`, 기존) 해당 범주 확률이 `0.6`(모델 카드 임계와 별개로 실시간용 값, 보정 곡선으로 확정) 이상이 **2회 연속**이면 "AI 가 맞혔어요!" 연출 + 경과 시간 표시. 오탐 방지를 위해 연속 2회를 요구한다.
5. 신뢰도 임계 미만이면 "음… 아직 모르겠어요" 상태 유지. 비난 문구 금지(A8 규칙 유지).
6. 맞히면 그림을 계속 그릴 수 있다(자동 제출·잠금 없음). 제출 시 기존 `aiGuess` 필드(`MISSIONS_API.md` 그림 틀 절)에 **그 시점의 최종 후보**를 담는 흐름은 그대로 유지한다.

### 1.3 범위/제약

- 대상 틀: `DRAW_SKETCH`, `DRAW_A_TO_B`(판정 기준은 `drawTo`, A8 규칙 그대로). 대상 지정(`[대상]`) 미션은 판정하지 않고 추측만 표시.
- 서버 API 변경 없음. 추론 결과·경과 시간은 저장·전송하지 않는다(`aiGuess` 최종 후보 제외).
- 범주(~50개)에 없는 주제는 "맞혔는지" 판정을 못 한다. 이 비율이 높으면 범주 확장(재학습, M1)이 필요하다 → §6 결정 1.

### 1.4 검증

- 단위: 디바운스/coalescing, 히스테리시스, 연속 2회 판정(순수 함수로 분리해 JVM 테스트).
- 수동: 범주 10개를 실제로 그려 "맞히기까지 걸린 획 수/초"와 오탐(엉뚱한 순간에 맞힘) 횟수 기록 → 임계 조정. 저사양 기기 프레임 드랍 확인.

## 2. AI 미션 검색

"고양이", "퇴근", "비 오는 날" 같은 키워드로 **지난 미션 내역** 중 관련된 것을 찾아 준다. 단순 포함 검색이 아니라 "비" → "우산", "장마" 같은 연관 미션도 나오게 한다.

### 2.1 검색 대상과 범위 (프라이버시·잠금 규칙 적용)

- 색인 대상: `missions.content`(+`template` 라벨, 틀 `params`의 `subject`/`word` 등 서버가 만든 문장). **사용자 제출물·댓글은 색인하지 않는다**(§0-2).
- 노출 범위: 요청자가 **멤버인 그룹**의 미션 중 **이미 마감됐거나 내가 제출한 미션**. 미션 문장 자체는 피드가 아니므로 잠금 대상은 아니지만, 결과에서 제출물(`submissions`)은 **내가 제출한 미션에 한해서만** 링크를 내려준다(기존 `GET /api/missions/{id}/submissions` 규칙에 위임, 423 그대로).
- 그룹을 나간 사용자는 그 그룹 미션을 검색할 수 없다.

### 2.2 방식 비교

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. LLM 질의 확장 + 형태소 검색 | 질의만 LLM 에 보내 유의어·연관어로 확장 → Lucene Nori(B11 도입)/MariaDB 로 매칭 | 사용자 콘텐츠가 LLM 에 안 감(질의만), 구현 작음 | 의미 검색 한계, 질의마다 LLM 호출 |
| B. 임베딩 벡터 검색 | 미션 문장 임베딩을 미리 계산·저장, 질의 임베딩과 코사인 유사도 | 진짜 의미 검색, 호출 비용 질의 1회 | 임베딩 모델/저장 선택 필요, Qdrant 는 MVP 범위 밖(`CLAUDE.md`) |
| C. 하이브리드 | A 로 후보 확장 + B 로 재순위 | 품질 최고 | 구성 복잡 |

**권장: 1단계 A → 필요하면 2단계 B.** 이유: 색인 대상이 미션 문장 수백~수천 개 수준이라 별도 벡터 DB 가 과하다. B 로 갈 경우에도 **Qdrant 는 쓰지 않고** 임베딩을 DB 컬럼(JSON/BLOB)에 저장해 애플리케이션 메모리에서 코사인을 계산하는 방식으로 시작한다(그룹별 미션 수가 작아 충분). Qdrant 도입은 별도 결정(`CLAUDE.md` 의 "명시 요청 전 구현 금지" 유지).

### 2.3 설계 (1단계 A)

```
GET /api/search/missions?q=비오는날&groupId=(선택)&limit=20
```

1. 질의 정규화(공백·특수문자·길이 ≤ 50자). 빈 질의/너무 짧으면 400.
2. **질의 확장**: LLM 에 **질의 문자열만** 보내 연관어 5~10개를 JSON 배열로 받는다. 서버 검증(길이·개수·금칙어), 실패/비활성/키 없음이면 **확장 없이 원 질의로 폴백**(B8 의 폴백 패턴과 동일). 확장 결과는 `(질의 → 확장어)` 로 짧게 캐시(TTL 24h)해 호출 수를 줄인다.
3. **매칭**: Nori 형태소 분석한 토큰으로 `content`를 매칭, 원 질의 토큰은 가중치 1.0, 확장어는 0.5. 점수순 정렬, 같은 점수는 최신 우선.
4. 응답: `[{missionId, groupId, content, template, missionDate, matchedTerms[], submitted(내가 제출했는지)}]`. 점수는 비노출.
5. 이유 문구("'우산' 때문에 찾았어요")는 `matchedTerms` 로 앱이 조립한다 — 확장어가 매칭됐음을 보여 주면 "AI 가 찾아줬다"는 체감이 생긴다.

### 2.4 데이터/스키마

- 1단계는 **스키마 변경 없음**(Nori 는 질의 시점에 `missions.content` 를 분석하거나, 성능이 필요하면 `mission_search_terms(mission_id, term)` 같은 보조 테이블을 추가 — 결정 보류).
- 2단계(임베딩) 도입 시: `mission_embeddings(mission_id PK, model, vector, created_at)`. 미션 발행 시 비동기로 계산(`AsyncConfig` 재사용), 그룹 삭제 시 먼저 삭제(기존 삭제 순서 규칙).

### 2.5 엣지 케이스

- 결과 0건 → 확장어로도 없으면 "관련 미션이 없어요" + 최근 미션 몇 개 제안(선택).
- 질의 인젝션: 질의는 LLM 에 **데이터로만** 전달(시스템 프롬프트에서 "질의어의 연관어만 JSON 으로 출력"으로 제한), 출력은 서버가 파싱·검증하고 SQL 에는 파라미터 바인딩만 사용.
- 그룹이 여럿일 때 `groupId` 미지정 → 내 모든 그룹, 결과에 그룹명 표시.
- LLM 비용 폭주 → 사용자당 분당 호출 제한 + 캐시.

### 2.6 검증

- 단위: 질의 정규화, 확장 출력 파싱/검증, 폴백, 가중 매칭 순서, **권한 필터**(타 그룹/나간 그룹/미마감 미션 비노출 테스트가 핵심).
- 평가(발표용): 질의 30개를 직접 만들어 "원 질의만" vs "확장 포함"의 top-5 적중률 비교표.

## 3. 얼굴 자동 블러 (선택적 모자이크)

사진 제출 전에 **기기에서** 얼굴을 찾아 모자이크한다. "자동"이지만 **사용자가 얼굴별로 켜고 끌 수 있다**(선택적).

### 3.1 왜 기기 안인가

- 원본 사진(얼굴 포함)이 서버에 올라가기 전에 처리하면 **서버에는 처리된 이미지만 존재**한다. 유출·삭제 이슈가 줄고 0번 원칙과도 일치한다.
- 서버/비전 서비스(CLIP)에 얼굴 검출을 추가할 필요가 없다.

### 3.2 동작

1. 대상: `PHOTO_NOW`, `PHOTO_GALLERY`, `PHOTO_COLOR` 제출 화면의 "올리기" 직전 단계.
2. 기기 내장 검출기로 얼굴 박스 검출 — Android: ML Kit Face Detection(온디바이스 모델), iOS: Vision `VNDetectFaceRectanglesRequest`. 외부 API 호출 없음.
3. 미리보기에서 검출된 얼굴마다 박스 표시, 기본값은 **설정에서 정한 모드**(결정 3): ① 모두 블러 ② 선택 안 함(사용자가 탭해서 블러) ③ 사용 안 함.
4. 박스를 탭하면 해당 얼굴 블러 토글. 놓친 얼굴은 **영역 직접 지정**(드래그 사각형)으로 추가.
5. 제출 시 **픽셀 자체를 변환한 비트맵**을 업로드한다 — 비가역 모자이크(픽셀화, 블록 크기는 얼굴 폭의 ~1/8, 최소 8px). 가우시안 블러는 약하면 복원 가능성이 있어 쓰지 않는다. 오버레이만 얹은 이미지를 올리지 않는다.
6. EXIF(위치 등)는 이미 제출 파이프라인에서 제거하는지 확인하고, 아니라면 이 단계에서 제거한다 → §3.5 확인 항목.

### 3.3 서버·API

- **변경 없음.** 서버는 블러 여부를 모른다(메타데이터 필드를 추가하지 않는다 — 신뢰할 수 없는 클라이언트 값이므로 의미가 없다).

### 3.4 기존 AI 와의 상호작용 (확인 필요)

- **사진-주제 적합도(B10, CLIP)** 임계값은 블러 없는 177장으로 평가됐다(`ml/vision-service/EVAL.md`). 얼굴 모자이크가 `PHOTO_NOW`("지금 이 순간 ○○") 점수를 낮출 수 있다. → 블러한 사진 몇십 장으로 점수 분포 이동을 측정하고, 크면 임계 재평가. 블러 때문에 "찰떡" 판정이 불리해지면 안 된다는 점이 관건.
- 별이의 점수 코멘트/반응은 영향 없음.

### 3.5 엣지 케이스·확인 항목

- 얼굴 미검출(측면, 마스크, 작은 얼굴, 그림 속 얼굴) → 수동 영역 지정 안내. "자동이 100% 보장된다"는 문구 금지(UI 에 "놓친 얼굴이 없는지 확인해 주세요").
- 얼굴이 많은 단체 사진: 검출·합성 시간, 메모리(원본 해상도 비트맵 2개) → 긴 변 기준 다운스케일 후 처리하는 기존 업로드 파이프라인 위치를 확인.
- 갤러리 발굴 사진에 타인 얼굴이 있는 경우가 가장 흔한 사용처 → `PHOTO_GALLERY` 에서 기본 모드를 "모두 블러"로 둘지 결정 3 에서 같이 정한다.
- **EXIF 제거 여부**(Android/iOS 각각) 확인 — 별도 작업이 필요할 수 있다.
- iOS/Android 검출기 차이로 결과가 다름 → 플랫폼별 수동 검수.
- 댓글 첨부 사진·프로필 사진은 1차 범위 밖(결정 3).

### 3.6 검증

- 단위: 박스 → 블록 크기 계산, 토글 상태 머신, 비트맵 변환 결과가 원본과 달라졌는지(박스 안 픽셀 분산 감소).
- 수동: 얼굴 1/3/10명, 측면, 마스크, 어두운 사진 각 5장씩 검출률 기록(발표용 수치).

## 4. 멀티 암드 밴딧 (틀 선택 최적화)

### 4.1 문제 정의

- **팔(arm)**: 발행 가능한 미션 **틀**(`hawe.mission.enabled-templates`, 현재 기본 7종).
- **선택 시점**: `MissionTemplateSelector` 가 슬롯마다 틀을 고를 때(지금은 시드 기반 무작위 + 제약).
- **보상**: 해당 미션에서 그룹 멤버들이 얼마나 **참여**했고 얼마나 **공을 들였는지**.
- **목표**: 그룹마다 "참여·정성이 높게 나오는 틀 위주"로 발행하되, 다른 틀도 주기적으로 시도(탐색)한다.

### 4.2 보상 설계

서버에서 **실제로 측정 가능한 값만** 쓴다. 그림 제작 시간은 클라이언트만 알고 서버는 신뢰할 수 없으므로(`MISSIONS_API.md` 그림 틀 절) 쓰지 않는다.

멤버 i 의 미션 보상 `r_i ∈ [0, 1]`:

- 미제출: `r_i = 0`
- 제출: `r_i = 0.6 + 0.2·effort_i + 0.2·engage_i`
  - `effort_i` (0~1, 틀별 정규화): 글 틀은 본문 길이(틀별 상한으로 클램프)·캡션 유무, 사진 틀은 B10 `fit_score` 의 0~100 환산값(있을 때), 그림 틀은 PNG 의 잉크 비율 같은 단순 지표(결정 4: 쓸지 여부), 별점·선택 틀은 `caption`(이유) 작성 여부.
  - `engage_i` (0~1): 그 제출물이 받은 반응+댓글 수를 **그룹 크기와 미션 평균으로 정규화** (인기 투표처럼 보이지 않게 완만한 상한).
- 기본 가중치 0.6/0.2/0.2 는 B11 활동 지수 공식 형식을 따른 초안이며 조정 가능.

미션 단위 보상 합: 팔 a 에 대해 `n = 대상 인원`, `R = Σ r_i`. 대상 인원 정의는 B9(`EXPERIMENT_TOPIC.md` §3)와 동일 — 열릴 때 그룹에 있던 사람 + 그 미션에 낸 뒤 나간 사람.

**지연 보상**: 마감 후에야 확정되므로 **닫힌 미션만** 갱신한다(B9 와 같은 기준). 갱신은 마감 후 스케줄러 잡이 처리한다.

### 4.3 알고리즘: 계층 Thompson Sampling

- 모델: 팔마다 `Beta(α, β)` — 멤버-미션 하나를 "성공률 r_i 의 시도"로 보고 `α += R`, `β += (n − R)` 로 갱신(분수 보상의 일반적 근사. 정확한 베르누이는 아니므로 §4.8 에 한계 명시).
- **계층(전역 prior → 그룹)**: 전 그룹을 합친 전역 분포를 만들고, 그룹 분포는 `α_g = α_global·κ' + 실측 α` 식으로 **수축(shrinkage)** 시킨다. 데이터가 적은 신규 그룹은 전역 평균을 따라가고, 쌓이면 그 그룹의 취향으로 이동한다. `κ` (prior 강도, 의사 관측 수) 초안 10.
- 선택: 후보(제약을 통과한 틀)마다 분포에서 표본을 뽑아 가장 큰 팔을 고른다. 시드는 `(그룹, 날짜, 슬롯)` 결정적 시드 — 같은 입력이면 같은 결과(기존 선택기의 재현성 유지, 테스트 가능).
- **탐색 하한**: 어떤 후보 팔도 선택 확률이 최소 `ε = 0.05` 아래로 내려가지 않게 한다(피로·고착 방지, "가장 높은 것만 계속"을 막음).
- **반복 패널티**: 같은 틀이 최근 3일 안에 나왔으면 표본값에 `×0.85`. 매체 순환 규칙이 있어도 같은 틀 반복이 가능하므로 별도로 둔다.

### 4.4 콜드스타트: AI 생성 시드 데이터

현재 사용자·미션 기록이 거의 없어 밴딧이 학습할 데이터가 없다. 이를 **AI 생성 시드로 prior 를 채우는 것**으로 해결한다.

1. **생성**: LLM 에 (관계 유형 × 틀) 조합마다 "이 틀을 이 그룹에 냈을 때 멤버별 참여 확률, 제출 시 정성 수준" 시나리오를 페르소나 단위로 만들게 해 합성 미션 로그(제출 여부, effort, engage)를 생성한다. 입력에 사용자 데이터는 쓰지 않는다 — 관계 유형과 틀 설명만 (0번 원칙 2).
2. **적재**: 합성 로그를 의사 관측(α, β)으로 환산해 **전역 prior** 로 넣는다. 합성 데이터는 `is_synthetic = TRUE` 로 구분하고 **실측 통계와 섞어 보고하지 않는다.**
3. **영향력 제한**: 합성 prior 의 의사 관측 수 총합을 팔당 `K_syn = 10` 이하로 제한하고, 실측이 쌓이면 가중을 감쇠(`K_syn · exp(−N_real/N0)`). 즉 시드는 초반 방향만 주고 곧 실제 데이터에 밀려난다.
4. **솔직한 한계 (문서·발표에 그대로 쓴다)**: LLM 이 만든 분포는 LLM 의 **믿음**이지 실제 사용자 행동이 아니다. 합성 시드는 "학습을 빨리 시작하는 prior"일 뿐 "효과가 검증된 결과"가 아니다. 효과 주장은 실측 데이터로만 한다(§4.7).
5. **관계 유형 사용 문제**: 시드를 관계 유형별로 만들어 prior 에 반영하면 `MISSIONS_API.md` §6-1 규칙 4(관계별 선호·가중치 없음, 확정)와 충돌한다. → 기본은 **관계 무관 전역 prior 하나**로 만든다(관계 변수를 시드 생성의 다양성 소스로만 쓰고 prior 는 평균을 낸다). 관계별 prior 를 쓰려면 규칙 4 변경 결정이 필요하다 → §6 결정 5.

### 4.5 데이터/스키마 (제안)

```
template_bandit_stats
  scope           ENUM('GLOBAL','GROUP')
  group_id        BIGINT NULL            -- GLOBAL 이면 NULL, FK groups
  template        VARCHAR(40)
  alpha_real      DOUBLE   beta_real DOUBLE
  alpha_syn       DOUBLE   beta_syn  DOUBLE      -- 합성 prior (is_synthetic)
  n_missions      INT                           -- 반영된 닫힌 미션 수
  updated_at      DATETIME
  UNIQUE (scope, group_id, template)

template_bandit_applied
  mission_id      BIGINT PK (FK missions)      -- 이미 보상이 반영된 미션(중복 갱신 방지)
  applied_at      DATETIME

missions (컬럼 추가)
  template_policy VARCHAR(10)                  -- 'BANDIT' | 'RANDOM'
  selection_prob  DOUBLE NULL                  -- 선택 시점의 근사 확률(오프폴리시 평가용)
```

- V1 직접 수정 + 로컬 DB 재생성이라는 현재 마이그레이션 방식을 따르되, 공유 DB 반영 전 baseline 정리 필요(기존 규칙).
- 그룹 삭제 시 `template_bandit_stats(scope='GROUP')`, `template_bandit_applied` 를 미션/그룹보다 먼저 삭제.
- 전역 통계에는 **그룹을 식별할 값이 없다**(집계만).

### 4.6 기존 구조와의 통합

- `MissionTemplateSelector` 의 **후보 계산(규칙 1~3: 풀, 매체 순환, 어제 매체 제외, 후보 부족 예외)은 그대로**이고, 후보 집합 안에서 **"무작위 선택" 자리만 밴딧 샘플링으로 교체**한다. 규칙 5(대상 지정)도 선택 후 단계라 변하지 않는다.
- **선택 자유도는 작다 (코드 확인, 2026-11-09).** 현재 `MissionTemplateSelector` 는 매체(PHOTO/TEXT/DRAW)를 먼저 정하고 그 안에서 틀을 고른다. 하루 1개면 어제 매체를 뺀 매체들의 틀 전체(기본 풀 7종 중 최대 5개)가 후보지만, **하루 2개 이상이면 슬롯이 매체를 고정(규칙 2)하므로 그 매체 안의 시작 틀만** 고를 수 있다. 상세는 `docs/TODO_2/D4-selector-integration.md`.
- 스위치: `hawe.mission.template-policy=random|bandit`(기본 `random` — 기존 동작·회귀 테스트 보존). 켜도 그룹당 닫힌 미션이 N(초안 10)개 미만이면 prior 위주라 사실상 탐색.
- **B9 실험(AI vs 랜덤 주제)과의 관계**: B9 의 전제는 "두 군의 틀 분포가 같다"이다. 밴딧은 `(그룹, 날짜)` 단위 군 배정과 **독립**으로 틀을 고르고 **두 군에 같은 선택기**를 쓰므로 이 전제는 유지된다. 단 시간에 따라 틀 분포가 이동하므로 B9 의 주 지표(그룹 안 날짜 쌍 비교)는 그대로 유효하되, 리포트에 `template_policy` 별로 층화해 본다.
- 밴딧이 "참여 높은 틀"만 계속 고르는 현상은 사실상 §4.3 의 ε 하한·반복 패널티로 제한한다. 그래도 한 틀의 점유율이 과도하면 상한(결정 6)을 둔다.
- 새 틀(예: A4 가 배포돼 설정에 추가된 틀)은 전역 prior 가 없다 → **낙관적 초기값**(Beta(1,1))으로 시작해 자연스럽게 탐색된다.

### 4.7 평가 (발표·논문용)

1. **오프라인 시뮬레이션**: 합성 환경(그룹별 숨은 참여율)에서 `random` vs `bandit(합성 prior 있음/없음)` 의 누적 후회(regret)·평균 참여율 곡선. 코드로 재현 가능하게 `ml/` 아래 두는 방안(결정 7).
2. **온라인 실측**: 사용자가 쌓이면 B9 와 같은 방식 — (그룹, 날짜) 단위로 `BANDIT` 날 vs `RANDOM` 날을 무작위 배정해 참여율 차이를 그룹 내 비교(대응 비교)로 본다. 이때 `selection_prob` 로 역확률 가중(IPS) 보정도 가능.
3. 합성 시드의 기여도: `K_syn=0` vs `K_syn=10` 으로 초기 N 일 참여율 비교.
4. 표본이 작으면 B9 처럼 `underpowered` 경고를 붙이고 "경향" 이상으로 주장하지 않는다.

### 4.8 한계·엣지 케이스

- **멤버 수가 적은 그룹**(2~3명)은 한 사람의 결석이 보상을 크게 흔든다 → prior 수축이 이를 완화하지만 신호가 약하다.
- **분수 보상의 Beta 근사**는 베르누이 가정이 아니다. 분산을 과소추정할 수 있어 탐색이 부족해질 수 있음 → ε 하한으로 보완. 엄밀 평가가 필요하면 Gaussian TS 로 대체(결정 보류).
- **비정상성**: 취향·시기(시험 기간)가 바뀐다. 오래된 관측을 지수 감쇠(반감기 초안 30일)로 약화.
- **신기함 효과**: 새 틀은 처음에 참여가 높을 수 있다 → 감쇠와 반복 패널티로 완화하되 한계로 명시.
- **교란**: 틀 외에 요일·마감 시각이 참여에 영향 → 요일을 문맥 변수로 쓰는 contextual bandit 은 2차 범위.
- 보상에 `engage`(반응·댓글)를 넣으면 인기 있는 사람이 많은 그룹이 유리 → 그룹 크기 정규화와 상한 클램프.
- 틀 풀이 1~2개로 줄어드는 설정에서는 후보가 없어 밴딧이 무의미 → 기존 후보 부족 규칙을 따름.

### 4.9 프라이버시

- 보상 계산은 서버 DB 안에서 끝난다(외부 전송 없음). 시드 생성 LLM 에는 사용자 데이터 미전송(§4.4).
- 리포트·전역 통계에 사람/그룹을 알아볼 값이 없다(B9 리포트 규칙과 동일).
