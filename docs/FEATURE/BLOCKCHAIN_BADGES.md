# 블록체인 디지털 배지 (업적) 설계 (초안)

작성: 2026-11-09. 상태: **설계 초안 — 구현 전.** 신규 기능 6~7개 중 하나. AI 기능은 [AI_FEATURES.md](AI_FEATURES.md).
구현 계획은 §11 열린 결정이 정해진 뒤 만든다.

## 1. 목표와 범위

- 앱에 **업적** 화면을 만들고, 조건을 달성하면 **서버가 판정**해 **블록체인에 디지털 배지를 발급**한다.
- 판정·발급·검증은 전부 서버사이드다. 앱은 목록/진행도를 보여 주고 "블록체인에서 확인" 링크를 연다. 사용자에게 **지갑·코인·가스비를 요구하지 않는다**.
- 배지는 **양도 불가(Soulbound)** 이고 금전적 가치가 없다. 판매·거래·교환 기능은 만들지 않는다.
- 범위 밖(1차): 사용자 본인 지갑으로 내보내기, 마켓/전송, 메인넷 운영, 알림 푸시(앱 안 알림만).

## 2. 블록체인이 주는 것 / 안 주는 것 (정직한 정리)

| 주는 것 | 안 주는 것 |
|---|---|
| 발급 사실의 **변조 불가한 공개 기록**(누가가 아니라 "이 익명 ID 가 이 시각에 이 배지를 받았다") | 서버 없이도 판정이 옳다는 보증 — **판정과 발급 주체는 여전히 우리 서버**(중앙화 발급자) |
| 서비스가 사라져도 남는 **이식 가능한 증명**, 탐색기에서 누구나 확인 | 개인정보 삭제 가능성(온체인 데이터는 지울 수 없다 → §6 로 대응) |
| 포트폴리오/발표용 "온체인 업적" 시연 | 비용 0 (테스트넷은 무료, L2 메인넷도 건당 소액 발생) |

발표·문서에서도 "탈중앙 보증"처럼 과장하지 않고 위 표대로 쓴다.

## 3. 체인 선택

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 퍼블릭 EVM 테스트넷** (Base Sepolia / Polygon Amoy 등) | ERC-721 SBT 컨트랙트를 테스트넷에 배포 | 무료, 탐색기 공개 검증, 구현 자료 풍부, web3j 사용 | 테스트넷은 초기화·중단 가능(영속성 보장 없음) |
| B. 퍼블릭 EVM L2 메인넷 | 같은 컨트랙트를 메인넷에 | 영속적, 건당 비용 소액 | 지갑 자금 관리·법적/스토어 검토 필요 |
| C. 사설/허가형 체인 (Besu 등) | 자체 노드 운영 | 비용·프라이버시 통제 | 운영 부담 큼, "공개 검증" 가치 약함 |
| D. 해시 체인 + 앵커링 | 서버 DB 의 append-only 해시 체인, 주기적으로 머클 루트만 퍼블릭 체인에 기록 | 건수와 무관하게 비용 거의 0, 개인정보 노출 최소 | "디지털 배지(토큰)" 느낌 약함, 사용자별 소유 증명 불가 |

**권장: A 로 시작, 컨트랙트·서버 코드는 체인 ID/RPC 만 바꾸면 B 로 옮길 수 있게 설계.** D 는 폴백/보강안(§12). 결정 1 에서 확정.

## 4. 아키텍처

```
 SubmissionCreatedEvent(after commit) ──┐
 매일/매월 스케줄러(스트릭·월 개근)  ─────┼─▶ AchievementEvaluator ──▶ user_badges(PENDING) + badge_mint_jobs(outbox)
                                         ┘          (DB 트랜잭션 안에서, 멱등)
                                                                  │
                                         BadgeMintWorker (비동기, 단일 스레드)
                                                │  서명(서버 발급 키) → RPC → 영수증 확인
                                                ▼
                                    user_badges(CONFIRMED, tx_hash, token_id)
                                                │
                              BADGE_EARNED 앱 안 알림 + GET /api/me/badges
```

- **DB 가 정본**, 체인은 "발급 증명 사본"이다. 판정은 DB 만 보고 하고 체인 장애가 제출·피드·도장 흐름을 막지 않는다 (B10 비전 서비스와 같은 원칙: 이벤트는 after-commit, 실패해도 본 요청은 영향 없음).
- 기존 이벤트 재사용: `SubmissionCreatedEvent`(제출), `GroupCreatedEvent` 등. 스트릭·월 개근처럼 "닫힌 미션"이 필요한 업적은 스케줄러가 판정한다(B9/B11 의 "닫힌 미션만" 기준과 동일).
- 패키지는 프로젝트 규칙대로 기능별: `com.sapphire.hawe.badge/{controller,service,dto,domain,dao}`. 체인 클라이언트(`BadgeChainClient`)는 `service` 에 두고 인터페이스로 분리해 테스트에서 가짜 구현을 쓴다. 새 하위 폴더는 만들지 않는다.
- `hawe.chain.enabled=false` 가 기본. 꺼져 있으면 업적은 판정·표시되지만 `ISSUED_OFFCHAIN`(체인 없이 DB 기록) 상태로 두고, 켜면 대기 중인 것을 이어서 발급한다(백필 가능).

## 5. 컨트랙트

- 표준: **ERC-721 + ERC-5192(Minimal Soulbound)**. `locked(tokenId) == true`, `transferFrom`/`approve` 는 revert. OpenZeppelin 기반, 새로 보안 로직을 짜지 않는다.
- 역할: `MINTER`(서버 발급 키) 만 `mint`. 소유자(`owner`) 는 별도 운영 키(발급 키와 분리).
- `mint(to, badgeType, seq)`: 같은 `(to, badgeType)` 이 이미 있으면 revert(**온체인 멱등**). 이벤트 `BadgeIssued(to, tokenId, badgeType, issuedAt)`.
- **회수/소각**: 발급자만 `burn` 가능 — 탈퇴 처리(§6)와 오발급 정정용. 소각도 온체인 기록으로 남는다는 점을 감안한다.
- `tokenURI` → 우리 서버의 공개 URL `https://<api>/badges/meta/{badgeType}.json` (**배지 종류별 정적 메타데이터**, 개인정보 없음). 이미지는 앱의 캐릭터/도장과 같은 SVG 계열 에셋을 서버 정적 경로에서 서빙(IPFS 는 1차 제외 — 결정 6).
- 컨트랙트 코드/테스트: 저장소 신규 디렉터리 `chain/` (Foundry 또는 Hardhat — 결정 7). 배포 주소·ABI 는 `chain/deployments/<network>.json` 로 커밋(키는 절대 커밋하지 않음).

## 6. 프라이버시와 탈퇴 (가장 중요한 제약)

온체인 데이터는 **삭제할 수 없다**. 그래서 애초에 지울 일이 없는 데이터만 올린다.

- 온체인에 올리는 것: 배지 종류 코드, 발급 시각, 토큰 ID, **의명 주소**. 올리지 않는 것: 이메일·닉네임·그룹 이름·그룹/미션/제출 ID·사진·글.
- **사용자 ↔ 주소 매핑은 서버 DB 에만** 있다. 주소는 사용자별로 서로 달라야(다른 사용자와 배지를 합쳐 추적 불가) 하고, 같은 사용자의 배지끼리는 같은 주소여야(소유 증명) 한다. → 서버가 HD 키 파생(`m/44'/60'/0'/0/{userIndex}`, `userIndex` 는 사용자 ID 가 아닌 무작위 일련번호)으로 **커스터디얼 주소**를 만들고, `user_chain_accounts(user_id, address, derivation_index)` 로만 연결한다. (대안: 주소 없이 한 컨트랙트에 `bytes32 hash(userSalt)` 를 소유자로 기록 — 결정 2.)
- **탈퇴**: ① 해당 사용자의 토큰을 `burn` ② `user_chain_accounts` 매핑 삭제 ③ `user_badges` 삭제(기존 탈퇴 쿼리 순서 규칙을 따름: 제출물보다 먼저가 아니라 `users` 삭제 전). 소각 후에도 과거 `BadgeIssued` 로그는 남지만 **익명 주소 + 배지 코드 + 시각**뿐이고 매핑이 사라져 사람을 식별할 수 없다. 이 점을 개인정보 처리방침에 문구로 명시(문구 확정은 팀).
- 서버 DB 유출 시: 매핑이 노출되면 주소 소유자가 식별됨 → 파생 마스터 시드는 DB 가 아니라 **시크릿 매니저(AWS Secrets Manager)** 에 두고, DB 에는 파생 인덱스만 저장.
- 이 기능은 LLM/외부 AI 로 사용자 데이터를 보내지 않는다(해당 없음).

## 7. 업적 정의와 판정

업적 종류(`badge_type`)는 **코드/설정 파일 카탈로그**로 관리한다(DB ENUM 사용 안 함 — 틀과 같은 이유로 추가 시 마이그레이션 불필요). 카탈로그 항목: `code`, 한국어 이름·설명, 조건 파라미터, 등급(`COMMON/RARE/EPIC`), 이미지 키, 반복 가능 여부(기본: 사용자당 1회).

초안 목록 (모두 **서버 DB 의 기존 데이터만으로 판정**; 출처 컬럼 참고):

| 코드 | 조건 | 판정 근거 | 시점 |
|---|---|---|---|
| `FIRST_SUBMISSION` | 첫 제출 | `submissions` | 제출 직후 |
| `SUBMISSIONS_10/50/100` | 누적 제출 N회 | `submissions` | 제출 직후 |
| `STREAK_7/30` | 연속 N일 제출 | 제출한 날 집합 (하루 여러 미션이면 "하루에 1개라도" 기준 — 결정 3) | 매일 스케줄러 |
| `PERFECT_MONTH` | 한 달 모든 미션 제출 | 닫힌 미션 전체 대비 제출 | 월 확정 후 |
| `EARLY_BIRD_10` | 마감 전·발행 후 1시간 내 제출 10회 | `is_late`, `published_at` | 제출 직후 |
| `PHOTO_PERFECT_5` | 찰떡 배지 5회 | `submission_ai_reviews` (B10, 점수는 비노출 유지: 개수만 사용) | 리뷰 완료 시 |
| `CROWD_FAVORITE` | 한 글이 반응+댓글 20개 이상 | `reactions`, `comments` | 일 1회 |
| `GROUP_100_DAYS`, `GROUP_1_YEAR` | 그룹 결성·COUPLE 시작일 기념 | `groups.created_at`/`start_date` | 매일 |
| `ALL_TEMPLATES` | 서로 다른 틀 7종 모두 제출 | `missions.template` | 제출 직후 |

- **멱등**: `UNIQUE (user_id, badge_code)`. 같은 이벤트가 두 번 와도 한 번만 발급(`INSERT IGNORE`, B10 리뷰와 같은 방식).
- **도장 기준과 일치**: 도장은 제출 존재 여부로 계산(`CLAUDE.md` 규칙)하므로 스트릭도 같은 기준. 지각 제출을 스트릭에 포함할지는 결정 3.
- **어뷰징 방지**: 업적 판정에서 "혼자 있는 그룹" 제출은 제외(그룹 멤버 ≥ 2 일 때 센다 — 결정 4). 서버 데이터만 쓰므로 클라이언트가 보낸 값은 신뢰하지 않는다. 그룹을 나가거나 지워도 이미 받은 배지는 유지.
- **과거 데이터 소급**: 기능 출시 시 기존 기록을 한 번 스캔해 소급 발급(관리 잡, 한 번에 대량 민팅하지 않고 큐로 천천히). 소급 여부는 결정 5.
- 진행도(`progress/target`)는 앱 표시용으로 서버가 계산해 내려준다(예: 연속 5/7일).

## 8. 데이터 모델 (제안)

```
user_badges
  id              BIGINT PK
  user_id         BIGINT NOT NULL            FK users
  badge_code      VARCHAR(40) NOT NULL
  status          VARCHAR(20) NOT NULL       -- EARNED | MINTING | CONFIRMED | FAILED | ISSUED_OFFCHAIN
  earned_at       DATETIME NOT NULL
  token_id        VARCHAR(80) NULL
  tx_hash         CHAR(66) NULL
  chain_id        INT NULL
  confirmed_at    DATETIME NULL
  UNIQUE (user_id, badge_code)

badge_mint_jobs                                -- outbox
  id              BIGINT PK
  user_badge_id   BIGINT NOT NULL            FK user_badges
  attempts        INT NOT NULL DEFAULT 0
  next_attempt_at DATETIME NOT NULL
  last_error      VARCHAR(500) NULL
  status          VARCHAR(20)                -- PENDING | SENT | DONE | DEAD
  tx_hash         CHAR(66) NULL              -- 전송했지만 확정 전
  UNIQUE (user_badge_id)

user_chain_accounts
  user_id         BIGINT PK                  FK users
  address         CHAR(42) NOT NULL UNIQUE
  derivation_index INT NOT NULL UNIQUE
```

- V1 직접 수정 + 로컬 DB 재생성이라는 현재 방식을 따르고 공유 DB 반영 전 baseline 정리가 필요(기존 규칙).
- 삭제 순서: 그룹 삭제는 영향 없음(배지는 사용자 소유). **탈퇴**에서 소각·매핑 삭제 포함(§6).

## 9. 발급 워커 (신뢰성)

- 단일 스레드 `badgeMintExecutor`(`AsyncConfig` 에 추가): **nonce 충돌을 피하려고 발급 키당 한 번에 한 트랜잭션**.
- 흐름: `PENDING` 잡 선택(`FOR UPDATE SKIP LOCKED` 또는 단일 인스턴스 가정) → `eth_estimateGas` → 서명·전송 → `tx_hash` 저장(`SENT`) → 영수증 폴링(확정 블록 수 N, 테스트넷 1~2) → `CONFIRMED`.
- **재시작 안전**: `SENT` 인데 `tx_hash` 가 이미 있으면 재전송하지 않고 영수증만 확인. 영수증이 없고 오래되면(드롭) 같은 nonce 로 가스 올려 재전송 또는 새로 전송 — 온체인 멱등(`(to,badgeType)` 중복 revert)이 중복 발급을 막는다.
- 재시도: 지수 백오프(30s→…→1h), 최대 8회 후 `DEAD` 로 표시하고 로그. 앱에는 상태가 `MINTING` 이어도 업적 달성은 **즉시 표시**하고 "블록체인 기록 중" 배지만 달리 보인다.
- **가스 잔액 모니터링**: 발급 키 잔액이 임계 미만이면 경고 로그(+ 내부 지표) 후 발급 중단(판정은 계속). 테스트넷은 faucet 으로 충전.
- 큐 오버플로/RPC 장애 시 판정을 막지 않는다. 자동 재처리는 스케줄러가 `PENDING`/`FAILED` 를 주기적으로 다시 집어 준다(B10 과 달리 재처리 있음 — 발급은 누락되면 안 되므로).

## 10. API / 앱

```
GET  /api/me/badges                 -- 획득 배지 목록 (code, name, tier, earnedAt, status, explorerUrl?, tokenId?)
GET  /api/badges/catalog            -- 전체 업적 + 내 진행도(progress, target, earned)
POST /api/me/badges/{code}/retry    -- (선택) FAILED 수동 재시도 — 1차 제외 가능
```

- 응답에 `explorerUrl`(예: 탐색기의 tx/token 링크)은 `CONFIRMED` 일 때만. 이메일·주소 등 **사용자 주소는 내려주지 않는다**(지갑 노출 불필요). 필요하면 결정 2 에서 재논의.
- 알림: `BADGE_EARNED` 앱 안 알림(`NOTIFICATIONS`), 이미지 키는 카탈로그 코드로 앱이 해석. 푸시는 알림 단계에서 연결.
- 다른 멤버 배지 노출: 그룹 멤버 프로필/목록에 대표 배지를 보여 줄지는 결정 8(기본: 본인 화면에서만).
- Android: 마이페이지 → "업적" 화면(그리드, 잠금/획득/진행도, 상세에서 "블록체인에서 확인" 외부 링크). iOS 는 A5 방식으로 이식. 디자인 없음 → 임시 아이콘(`임시` 주석).
- 앱스토어 정책: 코인 구매·전송·월렛 기능이 없는 "업적 배지 표시"로 설계해 문제 소지를 줄인다. 다만 심사 정책은 변동하므로 출시 전에 확인(§13 사용자 작업).

## 12. 폴백: 해시 체인 + 앵커링 (D안)

체인 연동이 막히거나 비용·운영 부담이 클 때: `user_badges` 에 `prev_hash`/`hash` 를 두어 발급 기록을 해시 체인으로 연결하고, 하루 1회 마지막 해시(또는 머클 루트)만 퍼블릭 체인에 기록한다. 변조 불가성은 유지되지만 사용자별 토큰은 없다. §7~§10 의 판정·API·앱은 그대로 쓴다 — 그래서 **판정 로직과 발급 매체(체인 클라이언트)를 분리**해 두는 것이 §4 설계의 핵심이다.

## 13. 위험·엣지 케이스

- **오발급**(판정 버그): `burn` + 재판정으로 정정. 소각 기록이 체인에 남음을 감수. 그래서 출시 초기엔 **발급 전 드라이런 로그**로 판정 결과만 점검.
- **키 유출**: 발급 키는 mint 권한만(소각도 가능하므로 owner 키와 분리·최소 권한), 시크릿 매니저·환경변수, `.env.example` 에는 이름만. 유출 시 `MINTER` 회수·교체 절차 문서화.
- **RPC 사업자 의존**(Alchemy/Infura 등): 키 과금·속도 제한 → 재시도/백오프, 두 번째 RPC 폴백은 2차.
- **테스트넷 초기화/폐쇄**: 배지 증명이 사라질 수 있다. 1차 목적(시연·학습)임을 명시하고, 메인넷 이전 경로를 컨트랙트 재배포 + 재발급 잡으로 열어 둔다.
- **동시성**: 같은 제출에서 여러 업적이 동시에 달성 — 업적마다 개별 잡, 단일 워커가 순차 처리.
- **시간대**: 스트릭·"하루" 는 기존 `mission_date` 기준(서버 시간대 일관).
- **규제/법적 검토**: 무가치·양도 불가·판매 없음으로 설계했지만 가상자산 관련 해석은 팀 책임으로 별도 검토.
- **서버 시간/재시작 중복 이벤트**: `UNIQUE` 와 온체인 멱등이 이중 방어.

## 14. 테스트·검증

- 단위: 각 업적 판정 순수 함수(경계: 6일/7일, 자정 경계, 하루 다중 미션, 지각, 1인 그룹), 멱등(`INSERT IGNORE` 2회), 상태 전이(`EARNED → MINTING → CONFIRMED`, 실패·재시도·`DEAD`), 탈퇴 시 소각·매핑 삭제 호출, 체인 클라이언트 가짜 구현으로 워커 재시작 시나리오.
- 컨트랙트: 전송 불가(`transferFrom` revert), 중복 발급 revert, 비-MINTER 호출 revert, `burn` 권한, `locked()`.
- 통합: 로컬 노드(Anvil/Hardhat node)에 배포해 서버가 실제로 민팅·영수증 확인까지 수행하는 테스트 1~2개(CI 필수 아님, 로컬 프로필).
- 수동: 테스트넷에서 실제 발급 후 탐색기 확인, 앱 업적 화면에서 링크 열기.
- 문서/보고에는 "체인 장애 시 제출 흐름 영향 없음"을 장애 주입 테스트(RPC 끊기)로 확인해 기록.

## 15. 구현 순서 제안

1. 업적 카탈로그 + 판정 + `user_badges` + API + 앱 업적 화면 (**체인 없이 `ISSUED_OFFCHAIN`**) — 가장 먼저 가치가 나오고 체인과 독립.
2. 컨트랙트(`chain/`) + 로컬 노드 테스트.
3. 발급 워커 + 테스트넷 연동 + 백필 잡.
4. 탈퇴 연동(소각·매핑 삭제), 운영 문서(키 교체·잔액·장애 대응).

의존: 1 은 `submission`, `mission` 모듈의 이벤트·조회만 사용. 탈퇴 로직(`UserWithdrawal` 계열)과 `AsyncConfig`, V1 마이그레이션이 다른 작업과 겹칠 수 있어 순서를 조율한다.
