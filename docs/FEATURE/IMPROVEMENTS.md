## 1. 아키텍처 효율화 (나중에 조사)

### 1.1 지금은 하지 않는다

사용자 결정: 지금은 조사도 변경도 하지 않는다. 아래는 **나중에 조사할 때 빈손으로 시작하지 않도록** 문서에 이미 적혀 있는 단서와 조사 방법만 모아 둔 것이다. 코드로 확인한 사실이 아니라 기존 문서의 기록이므로, 조사 때 현재 코드로 다시 검증한다.

### 1.2 문서에 이미 적힌 후보 지점 (미검증)

| 지점 | 출처 | 내용 |
|---|---|---|
| AI 호출이 발행 트랜잭션 안 | `MISSIONS_API.md` §6-2 | 호출하는 동안 DB 연결을 잡음. 그룹이 늘면 "생성을 트랜잭션 밖으로" 구조 변경 필요 |
| 발행 스케줄러가 매분 전체 그룹 순회 | `MISSIONS_API.md` §6 | 그룹 수가 늘면 스케줄러 개선 필요(EventBridge 전환 계획과 연결) |
| 인프로세스 비동기 실행기 | B10(`visionExecutor`), B11(`AsyncConfig`) | 큐 오버플로 시 작업을 버리고 재처리 없음. 새 기능(배지 발급, 검색 색인, 밴딧 갱신)도 각자 실행기/outbox 를 추가할 예정 → **공통 비동기 작업 방식**을 정할 필요 |
| 파일 저장소 | `BACKEND_DB.md` | 개발=로컬 디스크, 운영=S3 전환 예정. `FileStorage` 인터페이스 경계 |
| 별도 Python 비전 서비스 | B10 | 서버와 프로세스가 분리됨. 배포·장애 격리·타임아웃 정책 |
| 마이그레이션 | `00-README.md` | V1 직접 수정 + 로컬 DB 재생성 방식. 공유/운영 DB 전에 baseline 재정리 필요 |
| 알림 | `BACKEND_DB.md` | 앱 안 알림만 있고 푸시(FCM/APNs/SNS) 미구현 |
| 모듈 경계 | `CLAUDE.md` | 기능별 패키지(5개 하위 폴더). 기능 간 의존(`SubmissionService` 를 여러 작업이 동시에 건드림)이 늘고 있음 |

### 1.3 조사 방법 (제안)

1. **측정 먼저.** "효율적"의 기준부터 정한다: 응답 지연(p95), 발행 소요 시간, DB 연결 점유 시간, 그룹 수 증가에 따른 스케줄러 비용, 장애 격리(AI·비전·체인 장애가 핵심 흐름에 번지는가), 변경 용이성(여러 작업이 같은 파일에서 충돌하는 빈도 — git 이력으로 측정 가능).
2. 현재 코드의 요청 흐름 4개(제출, 피드, 미션 발행, 달력)를 추적해 병목·동기 호출·트랜잭션 범위를 표로 만든다.
3. 부하 시나리오(그룹 100/1000개, 멤버 평균 5명)로 발행 스케줄과 피드 조회를 측정한다.
4. 개선안은 "작은 것부터"(트랜잭션 분리, 공통 outbox, 인덱스) 비교표로 제시하고, 대규모 재구성(서비스 분리 등)은 측정 근거가 있을 때만 제안한다. 새 추상화는 근거 없이 도입하지 않는다.
5. 산출물: `docs/BACKEND/ARCHITECTURE_REVIEW.md`(측정 결과 + 권고 + 우선순위). 구현 계획은 그 뒤에 쪼갠다.

### 1.4 시점

신규 기능(밴딧·배지·검색)의 비동기 처리 방식이 각자 갈라지기 전에 **공통 작업 처리 방식만이라도** 먼저 정하는 게 비용이 가장 작다. 신규 기능 구현 착수 전에 조사 시점을 다시 정한다.

## 2. 미션 생성 프롬프트 개선

목표: 같은 입력에서 **더 재밌고, 검증을 한 번에 통과하고, 매번 다른 미션**이 나오게 한다.

### 2.1 현황 조사 (코드·프롬프트 파일에서 확인한 사실)

생성 경로: `AiMissionGenerator` → 시스템 프롬프트(파일 이어 붙임) + 입력 JSON → Claude(`submit_mission` 도구 강제) → `GeneratedMissionValidator` → 실패 시 재요청(기본 2회) → 고정 문장 폴백(`AI_FALLBACK`). 모델 `claude-haiku-5-5`, `temperature 0.9`, `max_tokens 400`.

**발견 1 — 프롬프트 파일이 코드/결정과 어긋나 있다 (최우선).**

| 항목 | HEAD 의 프롬프트 파일 | 실제 |
|---|---|---|
| 음성 틀 3종 (`VOICE_*`) 설명 | `mission-create-prompt.md`, `mission-template-prompt.md` 모두에 남아 있음 | 2026-10-12 음성 제거 |
| 슬라이더 틀 설명 | `mission-create-prompt.md` 에 남아 있음 ("슬라이더" 절과 결과 형식의 슬라이더 항목) | 2026-10-19 슬라이더 삭제 (`ef0a276` 에서 파일에서도 지웠음) |
| "놀리기 좋은 미션 만들기" 절, 관계별 놀리는 세기, "미션 예시" | **없음** | 2026-10-19 `674ede1` 에서 추가한 내용 (수정 기록에 사용자 요청으로 기재) |

`git diff 674ede1 HEAD -- src/main/resources/prompts/` 로 보면 이후 `ef0a276`(슬라이더 삭제)에서 슬라이더를 지웠는데, `6ae2882`("fix(frontend): 프론트 개선", `mission-create-prompt.md` 21줄 추가/43줄 삭제)에서 **그 앞 내용이 일부 되돌아가고 "놀리기" 절이 사라진 것으로 보인다.** 의도한 변경인지 병합 중 되돌아간 것인지는 이 조사만으로 단정할 수 없다 → **팀에 확인 필요** (§2.6 결정 1). 의도한 게 아니라면 가장 값싼 개선이 곧 복구다.

영향: 쓰이지 않는 틀 설명이 매 호출 토큰을 차지하고, 모델이 제거된 틀 용어를 섞을 위험이 있다. 반대로 사용자가 요청했던 "놀리기 좋은 미션" 지침이 지금은 AI 에게 전달되지 않는다.

**발견 2 — 프롬프트 구조.**
- 시스템 프롬프트 = 파일 2개 + `server-guide.txt` 를 `---` 로 이은 것. 파일끼리 충돌하면 "생성 프롬프트를 따르라", 서버 안내와 충돌하면 "결과 형식은 서버 안내를 따르라"처럼 **우선순위가 말로만** 정해져 있다.
- 틀별 안내 파일은 **이번에 쓰지 않는 틀까지 전부** 매번 보낸다(이번 호출은 틀 1개). 시스템 프롬프트는 캐시되므로 비용은 작지만, 모델이 관련 없는 지침 사이에서 주의가 분산된다.
- 같은 역할 소개가 두 파일에 중복("미션 출제자" / "미션 빈칸 작가"), 말투·대상 규칙도 두 곳에 있다. 수정 기록의 규칙 4("같은 내용을 다르게 말하지 않게")를 사람이 지켜야 한다.
- 수정 기록 파일 안내가 "Spring AI 가 중괄호를 값 자리로 읽는다"고 되어 있지만 현재 구현은 `RestClient` 직접 호출이다(Spring AI 미사용). 중괄호 금지는 지금은 **검증기가 AI 출력에 대해** 강제하는 규칙이다. (B12 `mission-ai-spring-ai-bedrock` 계획은 완료 표시가 없다 — 진행 여부에 따라 프롬프트 로딩 방식이 바뀐다. 순서 조율 필요, §2.6 결정 5.)

**발견 3 — 재시도가 학습하지 못한다.** 검증 실패 시 **같은 입력을 그대로** 다시 보낸다. 검증기의 실패 사유(`InvalidMission` 메시지)는 사유만 담고 AI 문장은 담지 않아 AI 에게 돌려줘도 안전하지만 지금은 쓰지 않는다.

**발견 4 — 다양성 장치가 문자 수준뿐이다.** 최근 미션과 중복은 두 글자 조각 자카드 유사도 ≥ 0.8 로만 막는다. 말은 달라도 **주제가 같은 미션**("오늘 먹은 것 중 …"을 표현만 바꿔 반복)은 못 막는다. 입력의 "최근 미션" 개수 상한은 코드로 아직 확인하지 않았다(`GroupContextBuilder`/`GenerationContext` 확인 필요).

**발견 5 — 측정 장치가 부분적이다.** 이미 있는 것: `missions.generation_source`(`AI`/`AI_FALLBACK`/`PLACEHOLDER`), `experiment_arm`, B9 리포트의 참여율·반응. 없는 것: **프롬프트 버전 기록**, 재시도 횟수·실패 사유 분포, 첫 시도 통과율, 사람 평가, 오프라인 비교 도구. 결과적으로 프롬프트를 바꿔도 좋아졌는지 알 수 없다(수정 기록에도 "테스트 결과" 외 지표가 없음).

**발견 6 — 입력 신호.** 이미 풍부함(요일, 관계, 틀, 대상 유무, 최근 미션, 특별한 날, 그룹 참여/반응 기록). 아직 안 쓰는 것: 그날의 몇 번째 슬롯인지/발행 시각대(하루 여러 개 미션 도입 후), 같은 날 먼저 열린 미션과의 관계(최근 미션에 섞여 들어가 구분 안 됨), 전체 그룹에서 반응이 좋았던 같은 틀의 문장(예시 소스).

**참고 — 안전 규칙.** 2026-10-19 사용자 결정으로 프롬프트의 안전 문구를 지웠고(수정 기록에 "팀 확인 필요"로 남음), 서버는 `blocked-words`(기본 비어 있음)와 형식 검증만 한다. 이 문서는 그 결정을 바꾸지 않는다. 다만 개선 효과를 볼 때 부적절한 미션 비율도 같이 센다(§2.3).

### 2.2 개선 후보 (가설 — 측정으로 채택 여부 결정)

우선순위는 "효과 대비 변경량" 기준이다. **수정 기록 규칙 5에 따라 한 번에 하나씩** 적용하고 §2.3 으로 비교한다.

| # | 후보 | 기대 효과 | 변경 범위 | 비용·위험 |
|---|---|---|---|---|
| P1 | **프롬프트 정합 복구**: 음성·슬라이더 설명 삭제, 2차 틀 표는 유지/삭제 결정, "놀리기" 절·예시를 복구할지 팀 확인 후 반영 | 토큰 절감, 오작동 제거, 요청했던 지침 복원 | 프롬프트 파일 | 낮음 |

| P6 | **주제 다양성**: 최근 미션에서 서버가 뽑은 키워드(Nori 형태소, B11 도입)를 "최근 자주 쓴 소재"로 입력에 넣고 피하게 함, 또는 AI 가 `topic` 한 단어를 같이 돌려주게 해 주제 중복도 검증 | 같은 주제 반복 감소 | 입력 조립(+ 도구 스키마) | 중간 |

| P8 | **샘플링/모델 조정**: `temperature` 0.7/0.9/1.0, 모델 Haiku vs Sonnet 비교 | 문장 품질/안정성 | 설정 | 비용↑(모델). 지연·단가 확인 |
| P9 | **말투 보정**: 유행어 예시 목록이 "억지 유행어"를 만들 수 있어 빈도 규칙(한 문장 최대 1개 등) 재도입 여부를 사람 평가로 판단 | 자연스러움 | 프롬프트 파일 | 낮음 |
| P10 | **프롬프트 단일 소스화**: 두 파일의 중복(역할·말투·대상)을 정리하고 파일 맨 위에 우선순위 규칙을 한 곳에만 둔다. 수정 기록 파일 안내(Spring AI 문구)도 현재 구현에 맞게 정정 | 불일치 재발 방지 | 프롬프트 파일/기록 | 낮음. P1 과 함께 |

권장 순서: **P1·P10(복구/정리) → 측정 장치(§2.3) → P2 → P3 → P4·P6 → P5 → P8**. 측정 장치 없이 P3 이후를 하면 효과를 구분할 수 없다.

### 2.3 측정 설계

세 층으로 본다.

1. **자동 지표 (오프라인 하네스)** — 고정된 입력 세트(`틀 × 관계 × 대상 유무 × 그룹 기록 유무` 약 60 케이스, 날짜·최근 미션은 고정)에 대해 후보 프롬프트로 케이스당 N=5 회 생성한다. 실제 API 키가 필요하므로 **기본 테스트에서 제외**하고(`pom.xml` surefire 의 `hawe.mission.ai.enabled=false` 유지) 별도 실행 스크립트/프로필로 둔다. 기록하는 값:
   - 첫 시도 통과율, 시도당 실패 사유 분포, 최종 폴백 비율
   - 길이 분포(60자 초과 시도 비율), `[대상]` 오용 비율
   - 다양성: 케이스 내 N개 결과의 평균 쌍별 유사도(`GeneratedMissionValidator.similarity` 재사용), 서로 다른 소재 수
   - 토큰·지연(입력/출력 토큰, 호출 시간)
2. **사람 평가 (블라인드)** — 변형마다 무작위 50개를 섞어, 팀원 2명 이상이 1~5점으로 `재미`, `자연스러움`, `이 틀에 맞는가`, 그리고 `부적절함(예/아니오)`를 채점. 평가자에게 어느 프롬프트인지 숨긴다. 평가자 간 일치도(코헨 카파 또는 단순 일치율)를 함께 보고한다. 이 단계가 "재밌는가"를 재는 유일한 방법이다.
3. **온라인 지표 (실서비스)** — 기존 B9 의 참여율·반응·첫 제출 시간을 그대로 쓰되 `missions.prompt_version`(신규 컬럼, 프롬프트 파일 해시 앞 8자리 또는 수동 버전 문자열)을 기록해 버전별로 층화한다. 서비스 사용자가 적으면 `underpowered` 경고를 붙이고 "경향"까지만 말한다(B9 와 같은 원칙).

판정 기준 예: 사람 평가 `재미` 평균이 기준선 대비 +0.3 이상이고 첫 시도 통과율·다양성이 나빠지지 않으면 채택. 수치는 기준선(§2.4 단계 1)을 측정한 뒤 확정한다.

### 2.4 진행 순서

1. **기준선 측정**: 현재 HEAD 프롬프트로 하네스 + 사람 평가 (복구 전 상태를 먼저 재야 복구 효과를 알 수 있다).
2. P1·P10 적용 → 재측정. (프롬프트 복구가 팀 의도와 맞는지 확인이 선행 — 결정 1.)
3. `prompt_version` 기록, 실패 사유·재시도 횟수 로깅(사유만, AI 문장 제외) 추가.
4. P2 → 재측정 → P3 → 재측정 …(한 번에 하나).
5. 채택된 최종 프롬프트를 수정 기록(`수정 기록용(후에삭제).md`)에 규칙대로 남기고, 이 문서에 결과 표를 추가.

### 2.6 제약

- B8 결정 #11 유지: AI 로 보내는 것은 날짜·관계·틀·미션 문장·기념일·미션 단위 집계뿐. P4/P6 에서도 사용자 글·댓글·닉네임·그룹 이름·대상 신원을 보내지 않는다.
- 결과 항목 이름(`content`, `category`, `params`)과 빈칸 키는 코드와 같아야 한다(수정 기록 규칙 2). P5/P6 에서 필드를 추가하면 검증기와 함께 바꾼다.
- 틀·대상은 서버가 정한다 — 프롬프트 개선이 이를 바꾸지 않는다.
- API 키·응답 본문·AI 문장은 로그에 남기지 않는다(현행 유지). 하네스 결과 파일에는 생성 문장이 들어가므로 저장소에 커밋하지 않는다(`.gitignore`).
- 한 번에 하나씩 변경하고 변경마다 기록(수정 기록 파일 규칙).
