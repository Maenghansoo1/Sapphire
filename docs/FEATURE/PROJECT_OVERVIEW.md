# HA'WE (하웨) — 프로젝트 소개

> 이 문서는 **프로젝트를 처음 보는 사람이나 AI**에게 HA'WE가 무엇인지 설명하기 위한 문서다. 저장소를 보지 못해도 이해할 수 있게 썼다.
> 상태 표기: **확정**(결정됨) / **초안**(임시로 정한 값) / **미정**(결정 필요) / **구현됨**(코드 있음) / **설계만**(문서만 있음).

## 1. 한 줄 요약

**그룹마다 매일 미션이 열리고, 내가 먼저 답해야 그룹원들의 답을 볼 수 있는 모바일 그룹 앱.**

- 이름: HA'WE (하웨). "하루, 날것 그대로 — today, raw as it is"라는 뜻.
- 꾸미지 않은 하루를 가볍게 나누는 것이 목적이다. 사진·음성·글·그림·슬라이더 같은 짧은 놀이 형태의 미션을 쓴다.
- 사용자는 모두 성인이다. 톤은 친구에게 말 거는 가벼운 반말.

## 2. 누가, 왜 쓰는가

- **사용자:** 연인, 가족, 친구처럼 이미 알고 있는 소규모 그룹. 그룹을 만든 사람(그룹장)이 멤버를 초대한다.
- **문제:** 소규모 그룹은 평소 연락이 뜸하거나 일상을 공유하는 일이 부담스럽다.
- **해결:** 정해진 시각에 가벼운 미션이 열리고, 답하면 서로의 답이 보인다. "남의 답이 궁금해서" 참여하게 되는 구조다.
- **그룹 관계** 5종: 연인, 가족, 친구, 웬수(티격태격하는 라이벌), 그저그런사이. 관계에 따라 어울리는 미션 톤과 금지 주제가 다르다 (§7).

## 3. 핵심 규칙

| 규칙 | 내용 |
|---|---|
| **잠금(제출해야 열람)** | 내가 그 미션에 답하기 전에는 그룹원의 답(피드)과 집계 결과를 볼 수 없다. 화면에서는 블러 처리된다. |
| **미션** | 그룹마다 하루에 N개(그룹이 설정)가 정해진 시각에 자동으로 열린다. 사용자가 만드는 것이 아니라 AI가 생성한다. |
| **제출** | 미션당 1인 1회. 틀(§4)이 요구하는 형식으로 낸다. |
| **마감과 지각** | 마감 시각이 지나도 제출은 가능하며, 지각(`isLate`)으로 표시된다. |
| **도장** | 날짜별로 "참잘했어요"(제출함) 또는 "벌점"(안 함)이 달력에 찍힌다. 별도 저장 없이 제출 기록으로 계산한다. 하루 미션이 여러 개일 때의 기준은 **미정**(임시: 하나라도 제출하면 참잘했어요). |
| **재촉** | 아직 안 낸 멤버에게 "콕찌르기" 또는 "똥뿌리기"를 보낼 수 있고, 알림이 간다. |
| **상호작용** | 게시물에 스티커 반응(토글)과 댓글(`@멘션`, 사진 첨부)을 남길 수 있다. |
| **알림** | 미션 도착, 콕찌르기, 댓글, 멘션 등. |
| **마이페이지** | 이번 달 달력의 날짜별 도장, 날짜별 상세, 프로필 캐릭터 선택. |

## 4. 미션 "틀(템플릿)"

미션은 **틀 + 빈칸 + 문장**으로 만든다. 틀은 놀이 방식이고, 빈칸은 그 틀이 요구하는 입력값이다.
예: 틀 `삼행시`, 빈칸 `제시어=퇴근길` → 미션 문장 "퇴근길로 삼행시 지어줘".

사용자가 답하는 매체는 5가지다.

| 매체 | 틀 예시 (총 21종 중 일부) | 제출물 |
|---|---|---|
| 사진 | 지금 이 순간, 갤러리 발굴, 색깔 사냥 | 이미지 + 캡션 |
| 음성 | 한 줄(특정 톤으로 읽기), 소리 흉내, 성대모사 | 짧은 음성(≤ 20초) |
| 글 | 삼행시, 한 단어 일기, 한 줄 후기, 밸런스 게임, 빈칸 채우기 | 글 / 별점 / A·B 선택 |
| 그림 | 30초 스케치, A를 B로 | 앱 그림판의 그림 |
| 슬라이더(클릭) | 내 위치는?, 취향 막대, 다수결 예측 | 0~100 위치 (+ 예측값) |

틀은 성격에 따라 나뉜다.

| 유형 | 설명 | 상태 |
|---|---|---|
| 단독 제출 | 각자 혼자 내면 끝 (사진, 음성, 삼행시 등) | 1차 |
| 대상 지정 | 그룹 멤버 한 명이 미션에 지목됨 (빈칸 채우기, 일부 그림) | 1차 (정책 검토 중) |
| 집계 | 제출값을 모아 평균·비율·순위를 보여줌 (밸런스 게임, 슬라이더) | 1차 |
| 순서·역할 | 앞사람 결과를 이어받거나 출제자/맞히는 사람이 나뉨 (끝말 이어쓰기, 갈틱폰, 제시어 바 등) | 2차, 별도 설계 필요 |

## 5. 그룹 설정 (하루 미션 수와 시각)

- 그룹장은 **하루에 열 미션 수**(1~5, 기본 1, 상한은 초안)를 정한다.
- 미션 순번(슬롯)별로 **발행·마감 시각**을 정할 수 있다. 지정하지 않은 슬롯은 서버의 기본 시각(발행 09:00, 마감 23:00 — 초안)을 쓴다. 그룹 자체에는 시각 설정이 없고 슬롯이 전담한다.
  - 예: 하루 3개, 1번은 지정 없음(09:00~23:00), 2번은 14:00~22:00, 3번은 19:00 발행(마감은 기본).
- 미션이 열릴 때 발행·마감 시각을 미션에 고정 저장한다. 이후 설정을 바꿔도 이미 열린 미션과 지각 판정은 바뀌지 않는다.

## 6. AI의 역할

LLM은 두 곳에서 쓴다. 제공사와 연동 방식은 **미정**이며(Spring AI 사용을 검토 중), 프롬프트 초안만 있다.

1. **미션 생성:** 발행 시각마다 `{문장, 카테고리, 틀, 빈칸 값}`을 만든다.
   - 입력: 오늘 날짜/요일, 그룹 관계, 최근 미션(문장·카테고리·틀), 카테고리 목록.
   - 날씨·사는 곳·멤버 이름 같은 정보는 주지 않으며, 짐작해서 넣지 않는다.
   - 서버가 결과를 반드시 재검증한다 (예: 삼행시 제시어가 정확히 3글자인가, 최근 미션과 같은 틀이 아닌가). 실패하면 재시도하고, 계속 실패하면 예비 미션을 쓴다.
2. **제출 판정:** 제출물이 미션에 "성의 있게 참여했는지"를 본다. 사진 실력, 목소리, 글솜씨, 그림 실력은 채점하지 않으며, 참여하려는 마음이 보이면 인정하는 것이 기본이다. 판정 결과가 도장에 영향을 주는지는 **미정**.
   - 음성은 음성 인식(STT)으로 글로 바꾼 뒤 판단하는 방식을 가정한다. 톤·흉내·노래 같은 소리 자체는 AI가 정확히 판정하기 어려워 판정 없이 운영하는 안을 검토 중이다.

## 7. 미션 안전 규칙 (AI 생성 시 지킬 것)

**모든 관계 공통 금지:** 폭력·자해, 성적 내용, 혐오·차별, 위험하거나 불법인 행동, 음주·도박 부추김, 외모·몸·체중, 돈, 위치·개인정보(집·학교·회사, 영수증 등), 다른 사람을 몰래 찍거나 녹음, 무거운 주제(이별·죽음·병·트라우마), 정치·종교 같은 편 가르기, 욕설·비속어, 이모지.

**좋은 미션 조건:** 오늘 안에 누구나 답할 수 있어야 하고(특별한 장소·준비물 불필요), 답하는 데 1~2분이면 되고, 한 번에 하나만 묻고, 한 문장(30자 안팎)이며, 사람마다 답이 달라 궁금해져야 한다.

**관계별 주의 (요약)**

| 관계 | 방향 | 피할 것 |
|---|---|---|
| 연인 | 다정하고 설레는 미션. 음성·그림 적합 | 감시(어디야, 누구랑), 질투, 상대가 해준 것 평가, 관계 점수 |
| 가족 | 따뜻하고 쉬운 미션. 사진·음성·슬라이더 적합 | 나쁘게 평가하는 미션 전부(가족이 해준 것일 수 있음), 잔소리 주제(결혼·취업·성적), 형제 비교 |
| 친구 | 장난·솔직함. 모든 방식 적합 | 특정 친구 한 명 놀리기, 서열 매기기, 뒷담화 |
| 웬수 | 서로 놀리는 재미는 살리되 상처는 금지. 그림·슬라이더 적합 | 바꿀 수 없는 것(외모·가족·학력·경제) 놀리기, 여러 명이 한 명을 공격, 실제 적대감 |
| 그저그런사이 | 어색함 풀기. 슬라이더 최적 | 사생활, 친한 사이 전제 표현, 얼굴·목소리를 많이 드러내는 미션 |

핵심 원칙: **"평가 대상이 그룹 안의 누군가가 만들었거나 준 것일 수 있으면, 나쁘게 평가하는 미션은 만들지 않는다."**

**검토 중인 위험 틀:** `빈칸 채우기(랜덤 사람 지정)`는 여러 명이 한 명에 대해 쓰는 구조라 위 규칙과 충돌할 수 있어 허용 범위(긍정적 문장만, 관계별 허용 등)를 정하는 중이다.

## 8. 기술 구성

| 영역 | 내용 | 상태 |
|---|---|---|
| 백엔드 | Spring Boot 4.1.1 (Java 25, Maven), MariaDB, MyBatis(어노테이션 SQL), Flyway 마이그레이션, JWT 인증(stateless) | |
| 프론트엔드 | Cordova 기반 하이브리드 앱. 12개 화면의 **정적 HTML 목업**(이동만 가능, API 연결 없음) | 목업 |
| 저장소 | 이미지·음성 파일: 개발=로컬 디스크, 운영=S3(서버가 파일을 직접 받아 내부에서 저장) | 설계 |
| 스케줄·푸시 | 미션 발행은 스케줄러(EventBridge), 푸시는 SNS | 설계 |
| 추후 | 회고 추천(Qdrant 벡터 검색, 과거 비슷한 감정의 글 찾기) | MVP 제외 |

- 로그인은 아이디/비밀번호 **자체 가입**이다 (소셜 로그인은 MVP 제외). 액세스 토큰 30분, 리프레시 토큰 14일.
- 코드 구조는 기능별 패키지(`auth`, `group`, `mission` …) 안에 controller → service → dao → domain/dto 계층을 둔다. 에러는 기능별 에러 코드 enum을 `BusinessException`으로 던져 전역 핸들러가 `{code, message}`로 응답한다.
- API는 REST(`/api/...`), JSON은 camelCase, 목록은 `{content, page, size, totalPages, totalElements}` 봉투를 쓴다.

## 9. DB 개요

사용자 → 그룹 가입 → 그룹별 미션 → 제출 → 댓글·반응이라는 흐름이다.

| 테이블 | 역할 |
|---|---|
| `users`, `characters` | 회원, 프로필 캐릭터 |
| `groups`, `group_members` | 그룹(하루 미션 수), 가입 관계(`owner`/`member`) |
| `group_mission_slots` | 슬롯별 시각 재정의 (바꾼 슬롯만 저장) |
| `missions` | 그날의 미션 (틀 코드 `template`, 빈칸 JSON `params`, 슬롯 번호, 발행·마감 시각) |
| `submissions` | 제출물. 틀에 따라 파일 / 글 / 숫자 / 선택 / 예측 칸 중 필요한 것만 채움 |
| `comments`, `comment_mentions`, `reactions` | 댓글, 멘션, 스티커 반응 |
| `pokes`, `notifications` | 재촉, 알림 |

DB가 중복을 막는 것: 한 그룹에 같은 사용자 중복 가입, 같은 슬롯 중복 발행, 한 미션에 한 사람의 중복 제출.

## 10. 현재 진행 상태

| 영역 | 상태 |
|---|---|
| 인증 API (가입·로그인·토큰 재발급) | **구현됨** |
| 그룹 API (생성·목록·상세·설정·멤버·초대·가입·나가기) | **구현됨** (하루 미션 수·슬롯 시각은 아직 반영 안 됨) |
| 미션·제출·집계 API | 설계만 |
| 댓글·반응·콕찌르기·알림·달력·캐릭터 API | 설계만 (DB 스키마는 있음) |
| 프론트엔드 | 화면 목업만, 백엔드 연결 전 |
| AI 연동 | 프롬프트 초안만, 코드 없음 |

팀은 사람(검토·git 관리)과 AI 에이전트 두 종류(구현, 리뷰·디버깅)로 역할을 나눠 작업한다.

## 11. 아직 정해지지 않은 것 (조언을 구할 만한 지점)

1. 하루 미션이 여러 개일 때 **도장 기준** (하나라도 / 모두 / 미션별).
2. **피드 잠금 단위**: 미션별로 제출해야 열람할지, 하루 단위로 풀지.
3. AI 판정 결과가 **도장에 영향을 주는지**, 불합격 시 어떻게 처리할지.
4. 음성 제출의 **판정 방식**(음성 인식 후 텍스트 판정 vs 판정 없음)과 외부 AI로 음성·사진을 보낼 때의 개인정보 처리.
5. **대상 지정 틀**의 허용 범위 (특정 멤버를 지목하는 미션이 괴롭힘이 되지 않게 하는 방법).
6. **순서·역할이 필요한 틀**(이어쓰기, 갈틱폰, 제시어 바)을 하루 안에 끝나는 구조로 어떻게 설계할지.
7. 하루 미션 수 상한, 슬롯 간 최소 간격, 마감이 자정을 넘기는 경우의 처리.
8. **시간대 기준**: "오늘"을 어느 시간대로 볼지 (DB와 서버를 한국 시간으로 통일할지).
9. 한 사람이 여러 그룹에 속할 때 달력·도장을 그룹 통합으로 보여주는 방식.
