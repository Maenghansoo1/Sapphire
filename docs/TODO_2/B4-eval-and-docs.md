# B4. AI 미션 검색 — 평가와 문서 갱신

> 범위: 측정 + 문서(코드 변경 최소). **선행: B2, B3.** 근거: `AI_FEATURES.md` §2.6.

## Goal

"질의 확장이 실제로 검색을 좋게 하는가"를 숫자로 보이고, 이 결과로 2단계(임베딩, B5) 필요 여부를 결정한다. 문서를 최신 구현에 맞춘다.

## Findings

- 평가 대상은 미션 문장 수백~수천 개 규모. 사용자 제출물은 검색 대상이 아니므로 평가 데이터에도 포함하지 않는다.
- 비교군: (1) 원 질의만(확장 비활성), (2) 질의 확장 포함. 같은 후보 집합에서 같은 정렬 규칙.

## Key Implementation Points

1. **평가 세트**: 팀원이 질의 30개를 만들고(일상어/동의어 위주: "비 오는 날", "퇴근", "야식", "고양이", "시험" …), 각 질의마다 **정답 미션 ID 집합**을 수작업으로 표시(후보 미션 200개 이상 풀에서). 파일은 `docs/FEATURE/` 아래가 아닌 비커밋 위치(`ml/eval-data/search/` 비커밋) 또는 미션 문장만이라 문제 없으면 CSV 로 커밋 가능(개인정보 없음 확인).
2. **지표**: top-5 적중률(정답이 상위 5개에 하나라도), recall@10, 질의당 결과 수 0건 비율. 확장 on/off 비교표.
3. **실행 도구**: 서비스 단위 테스트가 아니라 **측정용 임시 테스트/스크립트**(`src/test/…` 에 `-Psearch-eval` 같은 프로필 또는 JShell/main 클래스). 실제 LLM 호출이 필요하므로 기본 테스트에서 제외. 호출 결과(확장어)를 파일로 캐시해 반복 측정 시 재호출 없음.
4. **문서 갱신**: `docs/BACKEND/MISSIONS_API.md` 에 검색 API 절(요청/응답/권한 규칙/에러), `docs/FEATURE/PROJECT_OVERVIEW.md` 기능 소개 한 줄, `docs/BACKEND/BACKEND_DB.md` API 목록, `docs/FEATURE/AI_FEATURES.md` §2 에 "구현됨/측정 결과" 반영. 처리방침 메모: "검색어가 서비스 내부 AI 로 전송됨".
5. 결과 판정: 확장이 top-5 적중률을 의미 있게(예: +10%p 이상) 올리면 1단계로 종료, 아니면 B5 검토.

## Files / Functions to Change

문서 4곳, 측정 스크립트/프로필(선택), 평가 결과표(`docs/FEATURE/` 또는 `docs/BACKEND/`).

## Constraints

- 평가용으로 만든 모든 미션 데이터에 사용자 식별 정보 없음을 확인(미션 문장은 서버/AI 생성).
- 실제 LLM 호출은 사람이 키가 있는 환경에서 수행. 키/응답 본문을 저장소에 커밋하지 않는다(확장어 캐시는 질의→확장어만이면 커밋 가능, 판단은 팀).
- 커밋/푸시 금지.

## Edge Cases

- 정답 라벨러 간 불일치 → 2인 라벨 후 불일치 항목 합의.
- 표본이 작아 차이가 우연 → 표본 수와 "경향" 임을 명시, 질의별 승/패 수도 같이 표기.
- 후보 풀이 작음 → 시드 미션을 AI 로 대량 생성해 풀 확보(합성 데이터임을 표기).

## Tests Required / Validation Steps

문서 링크 유효성, 표의 수치 재현 방법(명령 1줄) 기재. 측정 도구가 테스트 코드면 기본 `./mvnw test` 에서 제외되는지 확인.
