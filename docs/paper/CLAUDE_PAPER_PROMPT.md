# 논문 초안 작성 마스터 프롬프트 (일반 Claude에 그대로 붙여 넣기)

## A. 역할

너는 컴퓨터공학 분야 학술 논문 작성 전문가다. 학부생 팀이 개발한 소프트웨어를 바탕으로 **한국인공지능융합기술학회(KAICTS) 학술대회**에 제출할 한국어 논문 초안을 작성한다. 너는 프로젝트 소스코드에 접근할 수 없다. 아래 D절의 프로젝트 정보가 사실의 전부이며, 여기에 없는 기능·수치·문헌을 만들어 내면 안 된다.

## B. 논문의 작성 목적

프로젝트를 기반으로 한 **소프트웨어 개발 연구 논문**이다. 단순한 앱 소개나 사용 설명서가 아니라 다음 흐름을 전달해야 한다.

**문제 제기 → 개발 필요성 → 시스템 설계 → 구현 방법 → 구현 결과 → 한계 및 향후 연구**

수준은 학부생이 작성하는 학술대회 논문이다. 개발 목적, 시스템 설계, 주요 기능, 적용 기술, 구현 결과를 명확히 전달하고, 불필요한 수식·어려운 용어·과장된 기여 주장은 피한다.

## C. 논문의 핵심 주제와 제목

- **핵심 주제**: "제출 후 열람" 규칙을 가진 소규모 그룹 일상 공유 앱에서, 서로 다른 위치에 배치한 세 가지 AI — (1) 서버가 구조를 정하고 LLM은 내용만 생성한 뒤 서버가 검증·대체하는 미션 생성, (2) 서버 측 사진–주제 적합도 평가, (3) 기기 안 그림 인식 — 를 설계·구현한 사례.
- **제목(확정안)**: LLM 기반 그룹 맞춤형 미션 생성과 경량 비전 AI 피드백을 적용한 소규모 그룹 일상 공유 앱 개발
- 영문 제목이 서식에 필요하면 다음을 쓴다: *Development of a Small-Group Daily Sharing App with LLM-Based Group-Tailored Mission Generation and Lightweight Vision AI Feedback*
- 서비스 이름: **HA'WE(하웨)** — "하루, 날것 그대로". 본문에서 "본 연구에서 개발한 HA'WE"처럼 쓴다.

## D. 프로젝트 상세 정보 (사실의 전부)

### D-1. 개발 배경과 서비스 개요
- 연인·가족·친구처럼 이미 아는 **소규모 그룹**은 평소 연락이 뜸해지고, 일상을 먼저 공유하는 것을 부담스러워한다는 문제의식에서 출발했다(팀의 기획 문제의식이며, 이를 뒷받침하는 통계나 선행연구는 확인되지 않았다).
- 그룹마다 매일 정해진 시각에 가벼운 **미션**(사진·글·그림)이 열리고, **자신이 먼저 제출해야 그룹원의 답을 볼 수 있다.** "다른 사람의 답이 궁금해서" 참여하게 만드는 구조다.
- 그룹 관계 5종: 연인, 가족, 친구, 웬수(티격태격하는 라이벌), 그저그런사이. 정원은 연인 2명, 그 외 최대 6명. 6자리 초대 코드로 미리보기 후 가입한다.
- 사용자는 성인이며, 앱의 말투는 친구에게 말하는 가벼운 반말이다.

### D-2. 핵심 서비스 규칙 (모두 구현됨)
1. **제출 후 열람(잠금)**: 미션에 제출하지 않은 사용자가 그 미션의 그룹 피드·게시물 상세·집계 결과를 요청하면 서버가 **HTTP 423 Locked**를 반환한다. 앱의 블러 처리는 표시용이고, 판정은 서버가 한다. 잠금은 미션 단위다.
2. **미션 발행**: 그룹이 하루 미션 수(1~5개)와 미션 순번(슬롯)별 발행·마감 시각을 정한다(기본 09:00 발행, 23:00 마감). 서버 스케줄러가 매 분 확인해 시각이 된 미션을 자동 발행한다. 발행 시 발행·마감 시각을 미션 데이터에 고정 저장해, 이후 설정을 바꿔도 이미 열린 미션의 판정이 바뀌지 않는다. DB 고유 제약으로 같은 슬롯의 중복 발행과 한 사람의 중복 제출을 막는다.
3. **제출**: 미션당 1인 1회. 마감 후에도 같은 슬롯의 다음 미션이 열리기 전까지 지각 제출할 수 있다. 서버가 형식을 검증한다(예: 삼행시는 빈 줄을 뺀 3줄이고 각 줄이 제시어 글자로 시작).
4. **도장**: 그룹 달력에 미션마다 "참잘했어요(마감 전 제출)/지각(마감 후 제출)/벌점(미제출이고 미션이 닫혔고 발행 당시 멤버였음)"이 표시된다. 도장은 **별도로 저장하지 않고 제출 기록에서 매번 계산**한다.
5. **상호작용**: 스티커 반응(토글), 댓글(@멘션), 미제출 멤버에게 "콕찌르기" 재촉(이미 제출한 사람·중복 재촉은 금지).
6. **알림**: 미션 도착, 콕찌르기, 댓글, 멘션 알림이 서버 DB에 생성되고 앱의 알림 목록·안 읽음 수로 확인한다. (휴대폰 원격 푸시 발송은 **구현되지 않았다**.)

### D-3. 미션 형식(틀)
미션은 "틀(놀이 방식) + 빈칸 + 문장"으로 구성된다. 운영 중 사용하는 틀 7종:

| 매체 | 틀 | 예시 |
|---|---|---|
| 사진 | 지금 이 순간(PHOTO_NOW), 갤러리 발굴(PHOTO_GALLERY), 색깔 사냥(PHOTO_COLOR) | "창밖 풍경을 찍어줘", "파란색 물건을 찾아 찍어줘" |
| 글 | 삼행시(TEXT_ACROSTIC), 빈칸 채우기(TEXT_FILL_BLANK, 그룹원 한 명을 대상으로 지정) | "퇴근길로 삼행시 지어줘" |
| 그림 | 30초 스케치(DRAW_SKETCH), A를 B로(DRAW_A_TO_B) | "구름을 풍선처럼 보이게 바꿔 그려줘" |

(코드에는 한 단어 일기·한 줄 후기·밸런스 게임 틀도 정의되어 있으나 기본 발행 목록에는 없다. 음성·슬라이더 미션은 개발 중 제거했다. 본문에서는 7종만 다룬다.)

### D-4. 기술 스택과 시스템 구성
- **클라이언트**: iOS 네이티브 앱(SwiftUI, iOS 17+), Android 네이티브 앱(Kotlin, Jetpack Compose, minSdk 26, CameraX, OkHttp). 두 앱 모두 서버 REST API에 연결되어 있다. 코드 규모는 Android 약 1만 1천 줄, iOS 약 1만 4천 줄.
- **서버**: Spring Boot 4.1 / Java 25, MyBatis(SQL 매퍼), Flyway 스키마 관리, Spring Security + JWT(액세스 토큰 30분, 리프레시 토큰 14일, 비밀번호 변경 시 기존 토큰 무효화). 기능별 패키지(인증, 그룹, 미션, 제출, 댓글, 반응, 콕찌르기, 알림, 달력, 인사이트 등) 안에 컨트롤러–서비스–DAO 계층을 둔다. 오류는 기능별 오류 코드로 통일된 `{code, message}` JSON으로 응답한다. Java 약 1만 300줄, 사용자용 REST API 약 45개.
- **데이터베이스**: 개발은 MariaDB, 운영은 MySQL(AWS RDS). 15개 테이블(사용자, 그룹, 그룹 멤버, 미션 슬롯, 미션, 제출, 제출 AI 리뷰, 댓글, 멘션, 반응, 재촉, 알림, 그룹 인사이트 캐시, 캐릭터 등).
- **파일 저장**: 개발은 로컬 디스크, 운영은 비공개 S3 버킷. 응답 시 1시간 유효한 서명 URL(presigned URL)을 발급한다.
- **비동기 처리**: 제출·댓글·재촉·미션 발행이 DB에 확정(커밋)된 뒤에만 이벤트로 알림 생성과 AI 피드백을 수행한다. 사진 평가와 AI 마스코트 댓글은 별도 스레드 풀에서 실행되므로 **제출 응답이 AI 처리를 기다리지 않는다.** AI 피드백이 실패해도 제출과 피드는 영향을 받지 않는다.
- **인프라**: AWS EC2(Amazon Linux 2023) 1대에 서버 jar 배포, RDS MySQL, S3(EC2 IAM 역할로 접근). 실습용 단일 서버 구성이다.
- **AI 구성 요소 3종**(D-5~D-7). 정리하면:

| 구성 요소 | 실행 위치 | 모델/기술 | 입력 → 출력 |
|---|---|---|---|
| 미션 문장 생성 | 외부 LLM API(게이트웨이 경유) | Claude 계열 LLM (Amazon Bedrock 경유) | 그룹 맥락 → 미션 문장·카테고리·빈칸 값 |
| 사진–주제 적합도 | 내부 Python 서비스 | CLIP ViT-B/32 이미지 인코더 + 다국어 텍스트 인코더, ONNX fp16 | 사진 + 주제어 → 적합도 0~1 |
| 그림 인식 | 사용자 기기 안 | 직접 학습한 소형 CNN, TFLite int8(Android) / Core ML(iOS) | 그림 → 50개 범주 확률 |

### D-5. LLM 기반 미션 생성 파이프라인 (핵심 기여)
설계 원칙: **"구조는 서버가 정하고, LLM은 내용만 채우며, 서버가 다시 검증하고, 실패하면 대체한다."**
1. **틀 선택(서버)**: 그룹 ID·날짜·슬롯 번호로 만든 결정적 시드로 틀을 고른다. 하루 1개면 어제와 다른 매체, 하루 여러 개면 같은 날 매체가 겹치지 않게 돌아가며 고른다. 같은 입력이면 항상 같은 결과가 나와 재현할 수 있다. 대상 지정 미션은 서버가 대상 멤버를 정한다. LLM은 틀을 고르거나 바꾸지 않는다.
2. **맥락 구성(개인정보 최소화)**: LLM에 보내는 정보는 오늘 날짜·요일, 그룹 관계 유형, 선택된 틀과 빈칸 정의, 대상 유무, 최근 미션 문장, 카테고리 목록, 특별한 날(연인 100일 단위·주년, 그룹 기념일 등), 미션 단위 참여율·반응 수뿐이다. **멤버 이름·닉네임, 그룹 이름, 제출한 글·사진·댓글은 보내지 않는다.** 대상 멤버는 `[대상]` 자리표시자로만 전달하고, 앱에 표시할 때 서버가 닉네임으로 바꾸며 받침에 맞게 조사(을/를, 이/가 등)를 보정한다.
3. **구조화된 출력**: LLM에게 도구(tool) 하나를 반드시 호출하게 해 `{content, category, params}` JSON으로 결과를 받는다. 긴 시스템 프롬프트는 캐시해 반복 호출 비용을 줄인다. 프롬프트에는 관계별 톤과 금지 주제(폭력·성적 내용·외모·돈·개인정보·무거운 주제 등, 그룹 안 누군가가 만든 것을 나쁘게 평가하는 미션 금지)가 들어 있다.
4. **서버 재검증**: 결과 항목 구성, 문장 길이(60자 이하), 카테고리가 목록에 있는지, 금지어, 틀별 형식(삼행시 제시어가 한글 세 글자이고 문장에 포함되는지, 빈칸 채우기의 빈칸이 정확히 하나인지, 대상 미션에 `[대상]`이 있는지), 최근 미션과의 문자 bigram 유사도가 0.8 이상이면 거절한다.
5. **재시도와 대체**: 검증 실패·통신 오류 시 전체 제한 시간 안에서 재시도하고, 그래도 실패하면 미리 준비한 예비 문장으로 발행한다. 따라서 **AI 장애가 미션 발행을 막지 않는다.** 미션마다 생성 출처(AI / AI 실패 후 예비 문장 / 예비 문장)를 기록한다.
6. **동작 확인**: AWS 배포 환경에서 AI가 생성한 미션(생성 출처 AI)이 발행되는 것을 확인했다. 실제 생성 예: "지금 내 손 닿는 곳에서 제일 만만한 물건 찍어 와".
7. **비교 실험 구조(실험은 아직 수행하지 않음)**: AI 주제와 예비 문장(랜덤) 주제의 효과를 비교하기 위해 (그룹, 날짜) 단위로 해시 기반 무작위 블라인드 배정을 하고, 틀·대상·시각은 두 군이 같게 하며, 참여율·정시 제출 비율·반응 수·첫 제출까지 시간을 그룹 내 비교(신뢰구간·부호 검정)로 분석하는 리포트 기능을 구현했다. **실제 사용자 데이터로 실험한 결과는 없다.**

### D-6. 사진–주제 적합도 평가
- 사진 미션(지금 이 순간, 색깔 사냥) 제출 후, 서버가 사진과 주제어를 내부 Python 비전 서비스(FastAPI)로 보낸다. 서비스는 CLIP ViT-B/32 이미지 인코더와 다국어 텍스트 인코더로 "주제 1개 + 대조 주제(일상 주제 72개 또는 다른 색 10개)" 중 이 주제일 확률을 계산해 적합도(0~1)만 돌려준다. 사진은 저장하지 않으며 외부 AI API로 보내지 않는다.
- 서버는 틀별 임계값으로 "찰떡상" 배지와 칭찬 문구를 정한다. 임계값은 정밀도 95%(배지)와 85%(칭찬) 기준으로 골랐다(지금 이 순간 0.024/0.017, 색깔 사냥 0.132/0.104). **점수가 낮아도 부정 평가는 보여 주지 않고 격려 문구만 주며, 도장은 제출 여부로만 정한다.**
- 결과는 AI 마스코트 "별"이 게시물에 댓글로 남긴다(0~100 점수 표시).
- 평가(팀원 2명이 찍은 사진 177장, 맞는 짝·안 맞는 짝 1:1, 총 1,028쌍): ROC-AUC 지금 이 순간 **0.958**, 색깔 사냥 **0.959**. CPU 기준 응답 지연 중앙값 약 0.42초.
- 경량화: PyTorch 대신 ONNX Runtime + fp16 모델로 바꿔 설치 용량 약 2.3GB → 0.7GB, 시작 시간 36초 → 2초로 줄였고, 5,140쌍에서 배지·문구 판정이 바뀐 경우는 0건이었다.
- 개발 중 문제 해결 사례: Java HTTP 클라이언트가 보낸 HTTP/2 업그레이드 요청을 Python 서버가 400 오류로 거절해 평가가 항상 실패하던 문제를 발견하고, HTTP/1.1로 고정한 뒤 실제 클라이언트로 재현하는 회귀 테스트를 추가했다.

### D-7. 온디바이스 그림 인식 ("AI가 맞혀볼게요")
- 그림 미션에서 사용자가 "AI에게 보여주기"를 누르면 **휴대폰 안에서** 그림이 무엇인지 맞힌다. 상위 3개 추측(라벨·확률)만 제출과 함께 서버로 보내고, AI 마스코트 "별"이 "○○인가요?" 댓글로 남긴다.
- 데이터: Google Quick, Draw! 데이터셋(CC BY 4.0)의 획 좌표 데이터에서 앱 미션 주제와 겹치는 50개 범주, 범주당 30,000장 → 학습 120만 / 검증 15만 / 테스트 15만 장.
- 전처리: 학습 코드와 앱이 같은 전처리 명세를 따른다(잉크 영역 경계 상자로 자르기 → 정사각형 가운데 배치 → 20×20 면적 평균 축소 → 28×28). 학습 측에서 만든 기준 입력 10개를 Android 단위 테스트가 같은 결과(칸당 오차 0.001 이하)로 만드는지 확인한다. 학습 그림에는 선 굵기(3~20px)·회전(±10°)·가로세로 비율(±10%) 증강을 적용했다.
- 모델: 사전학습 없이 처음부터 학습한 소형 CNN(3×3 합성곱 32·32·64·64·128 + 배치 정규화 + 전역 평균 풀링 + 드롭아웃 + 완전연결 50, 파라미터 146,258개). Google Colab T4 GPU, AdamW, 코사인 학습률 감소, 라벨 스무딩 0.05, 30 epoch.
- 경량화: TFLite float32(573KB) / float16(292KB) / int8(158KB)를 비교하고, "원본 대비 top-1 정확도가 1%p 넘게 떨어지지 않는 것 중 가장 작은 것" 규칙으로 **int8(158KB)**을 선택했다(정확도 유지).
- 결과: Quick, Draw! 테스트셋 top-1 **93.1%**, top-3 **98.4%**. 팀원 3명이 앱과 같은 방식의 그림판으로 직접 그린 206장에서 top-1 **86.4%**, top-3 96.1%(데이터셋과의 차이 6.7%p). PC에서 추론 시간 중앙값 약 1.2ms(휴대폰 실측은 하지 않음).
- "잘 모르겠어요" 기준: 1등 확률이 0.55 미만이면 답하지 않는다. 범주 밖 그림 43장을 포함해, 맞힌 답 +1·틀린 답 −1·모름 0으로 계산한 점수가 가장 높은 값으로 골랐다(이때 범주 안 그림의 86.4%에 답하고, 답한 것의 정확도 94.9%).
- "A를 B로" 미션은 A나 B 중 하나를 맞히면 성공으로 처리한다.

### D-8. 부가 기능 (구현됨, 본문에서는 짧게)
- 그룹 월간 인사이트: 활동 지수 = 100 × (0.6×참여율 + 0.2×정시 제출률 + 0.2×상호작용), 가장 빨리 제출한 멤버, 반응이 많은 글, 한국어 형태소 분석기(Lucene Nori)로 글 미션에서 추출한 자주 쓴 명사. 결과는 비동기로 생성해 캐시하며, 제출 원문은 캐시에 저장하지 않는다.
- 프로필 캐릭터, 그룹 내 프로필, 비밀번호 변경, 회원 탈퇴.
- 발행·마감·도장처럼 시간에 따라 달라지는 기능을 검증하기 위한 개발자 도구(가상 시계, 시드 데이터, 미션 강제 발행).

### D-9. 검증 현황 (논문에 쓸 수 있는 결과)
- 서버 자동화 테스트 약 360개(2026-10-20 로컬 실행 기록: 363개 실행, 실패 0), Android 단위 테스트 192개 통과(2026-10-19 기록), ML 코드 pytest 테스트.

### D-10. 한계 (논문 Ⅲ장에 반영)
1. 실제 사용자 실험이 없어 서비스가 그룹 참여를 높이는지는 검증되지 않았다.
2. 사진(177장, 2명)·그림(206장, 3명) 평가 표본이 작다. 사진의 "안 맞는 짝"은 관련 없는 주제로 만들어 실제보다 쉬울 수 있다.
3. 휴대폰 원격 푸시가 없어 미션 도착을 앱을 열어야 알 수 있다.
4. 단일 서버·HTTP 통신 등 운영 보안과 확장성이 실습 수준이다. AI 미션 생성은 발행 처리 안에서 외부 응답을 기다리므로(제한 시간 있음) 그룹이 많아지면 지연될 수 있다.
5. iOS 앱은 Android에서 수정한 일부 개선 사항이 아직 반영되지 않았다.

### D-11. 향후 연구
1. 구현해 둔 블라인드 비교 실험으로 AI 주제와 랜덤 주제의 참여율·상호작용 차이를 실제 사용자 그룹에서 측정.
2. 평가 데이터 확대와 비슷한 주제끼리의 구분 평가, 휴대폰 실기기 추론 성능 측정.
3. 원격 푸시, HTTPS 등 운영 환경 보완, AI 호출을 발행 처리와 분리하는 구조 개선.
4. LLM이 만든 미션의 안전성·재미를 평가하는 방법 연구, 이어쓰기처럼 순서가 있는 미션 확장.

## H. 작성 시 유의사항

1. **구현 범위 준수**: D절에 "구현됨"으로 적힌 것만 구현된 기능으로 쓴다. 원격 푸시, 참여율 비교 실험 결과, 사용자 설문, 부하 테스트, 휴대폰 실측 추론 시간은 **없는 것**이다.
2. **수치는 D절 그대로**: 새 수치를 만들거나 반올림 방식을 바꿔 다른 값처럼 보이게 하지 않는다. 퍼센트와 표본 수를 함께 쓴다(예: "206장에서 top-1 86.4%").
3. **효과 주장 금지**: "참여율을 높였다", "만족도가 향상되었다", "기존 서비스보다 우수하다"라고 쓰지 않는다. 대신 "~하도록 설계하였다", "~를 기대할 수 있으며 향후 실험으로 검증할 예정이다"로 쓴다.
4. **독창성 과장 금지**: Spring Boot·JWT·CLIP 같은 기존 기술을 쓴 것 자체를 기여로 주장하지 않는다. 기여는 "구성 방식"(서버 주도 제한형 생성·검증·대체, 개인정보 최소 입력, AI 배치 위치 분리, 학습–앱 전처리 일치 검증, 정밀도 기준 임계값 선택)에 둔다.
5. **문체**: 객관적인 학술체 "~하였다", "~이다". 1인칭 대신 "본 연구에서는", "본 논문에서는". 가벼운 반말 예시 문장은 따옴표 안의 미션 예시에만 쓴다. 영어 약어는 처음 나올 때 풀어 쓴다(예: 대규모 언어 모델(LLM)).
6. **소개문·설명서처럼 쓰지 않기**: "버튼을 누르면 ~ 화면이 나온다" 같은 조작 설명은 최소화하고, 각 기능을 "왜 필요한가 → 어떻게 설계했는가 → 무엇이 확인되었는가" 순서로 쓴다.
7. **분량**: 참고논문 서식의 쪽수 제한을 따른다. 정보가 없으면 A4 2단 기준 4쪽 안팎(본문 약 4,000~5,500자, 그림 4개, 표 2개)을 목표로 하고, 넘치면 D-8 부가 기능과 개발자 도구 설명부터 줄인다.
8. **고유 명칭**: 서비스명 HA'WE, 마스코트 "별", 틀 이름(지금 이 순간, 색깔 사냥, 삼행시 등)은 그대로 쓴다. 팀원 실명은 쓰지 않는다("팀원 3명").
9. 정보가 부족해 판단할 수 없는 부분은 추측하지 말고 `[확인 필요: 내용]`으로 남긴다.

## I. 최종 출력 요구사항

1. 바로 검토·수정할 수 있는 **한국어 논문 초안 전체**를 Markdown으로 출력한다: 제목 → 저자 자리표시 → (요약·키워드) → Ⅰ. 서론 → Ⅱ. 연구내용과 방법(소절 포함) → Ⅲ. 결론 및 향후 연구 → ACKNOWLEDGMENTS 자리표시 → REFERENCES.
2. 그림·표는 본문 해당 위치에 캡션과 `[그림 제작 필요: ...]` 메모로 넣고, 표 1·표 2는 실제 표로 작성한다.
3. 초안 뒤에 다음 두 목록을 붙인다.
   - **검토 체크리스트**: 초안에서 `[참고문헌 필요]`, `[서지 확인 필요]`, `[확인 필요]`를 단 위치 목록
   - **분량 조절 제안**: 줄이거나 늘릴 때 우선순위
4. 초안을 다 쓴 뒤 스스로 점검한다: D절에 없는 기능·수치·문헌이 들어갔는가? 효과를 단정한 문장이 있는가? 연구 목적(서론)과 구현 결과(Ⅱ-5)·결론이 서로 대응하는가? 문제가 있으면 고친 뒤 출력한다.
