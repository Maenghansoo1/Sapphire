# B15. 멀티암드 밴딧으로 미션 틀 고르기 (서버)

> 범위: 서버(+ 시뮬레이션용 Python 스크립트). 앱 변경 없음. 작성 2026-11-09.
>
> **목표 한 줄**: 지금은 미션 틀(삼행시, 갤러리, 색깔 사냥 …)을 정해진 규칙과 무작위로 고른다. 이걸 **그룹마다 참여율이 높고 공을 많이 들인 틀을 점점 더 자주** 내되, 가끔은 다른 틀도 시도하는 **멀티암드 밴딧(Thompson Sampling)** 으로 바꾼다. 효과는 A/B 실험으로 숫자로 확인한다.

## 용어 (처음 보는 사람용)

- **팔(arm)**: 고를 수 있는 선택지 = 미션 틀 하나.
- **보상(reward)**: 그 틀로 낸 미션이 얼마나 잘 됐는지 0~1 점수(참여율 + 공들인 정도).
- **탐색 / 활용**: 지금까지 좋았던 틀을 내는 것(활용)과, 아직 잘 모르는 틀을 시도해 보는 것(탐색) 사이의 균형.
- **Thompson Sampling**: 틀마다 "보상이 이쯤일 것"이라는 분포를 두고, 매번 분포에서 숫자를 하나씩 뽑아 가장 큰 틀을 고르는 방법. 잘 모르는 틀은 분포가 넓어서 가끔 뽑힌다 → 탐색이 자동으로 된다.

## Goal

- 그룹마다 틀별 보상 기록을 쌓고, 그걸로 틀을 고른다.
- 지금 규칙(어제와 다른 매체, 같은 날 같은 틀 반복 방지, 매체 돌리기)은 지킨다.
- 기능 스위치(기본 꺼짐) + 그룹 단위 A/B 실험으로 "밴딧 그룹 vs 기존 그룹" 참여율을 비교한다.
- 실제 적용 전에 **시뮬레이션**으로 효과(후회 곡선)를 보여 준다(포트폴리오 그래프).

## Findings (2026-11-09 코드 기준)

- 틀 선택: `MissionTemplateSelector.select`(49줄) — 그룹·날짜·슬롯 시드로 결정, 어제 매체 제외, 하루 여러 개면 매체 순서대로. 발행은 `MissionPublisher.publish`(147줄)에서 호출. 같은 날 다시 돌려도 같은 결과(테스트 `MissionTemplateSelectorTests` 의 지문 값으로 고정).
- **보상 재료가 이미 있다**: `MissionMapper.findClosedStatsByGroupId`(미션 AI 의 "그룹 기록"용) — 마감된 미션별 참여율과 반응·댓글 수(`engagement_count`)를 계산하고, **마스코트(`users.is_ai = 1`, V4) 반응·댓글은 뺀다**. 계산 함수는 `GroupContextBuilder.signals`(51줄).
- "공들인 정도"로 쓸 수 있는 값(`submissions` 테이블): 글 답 길이(`answer_data`), 캡션 유무(`caption`), 제때 냈는지(`is_late`), 발행 후 제출까지 걸린 시간(`submitted_at - published_at`), 받은 반응·댓글 수(마스코트 제외), 사진 주제 점수(`submission_ai_reviews.fit_score`).
- A/B 실험 틀: B9 `ExperimentAssigner.assign`(31줄) — `(그룹, 날짜)` 단위, SHA-256(salt|그룹|날짜). 밴딧은 **그룹 단위**로 배정해야 한다(같은 그룹이 날마다 정책이 바뀌면 학습이 안 됨) → 새 salt·단위로 따로 만든다.
- 그림 매체는 지금 틀이 하나("A를 B로")라 밴딧이 고를 게 없다(30초 스케치 중단). 매체 안에서 고르는 경우 의미가 작다 → 아래 Key Point 1 참고.
- DB 변경 파일은 V4 까지 있다 → 이 작업은 다음 번호.

## Key Implementation Points

1. **무엇을 고르나**: 기본안은 **매체는 지금 규칙(어제 매체 제외·돌리기)대로 정하고, 그 매체 안의 틀을 밴딧이 고른다.** 매체까지 밴딧이 고르면 매체가 한쪽으로 쏠릴 수 있어서다(대안은 3단계에서 시뮬레이션으로 비교).
2. **보상 정의** (0~1, 설정으로 가중치 조정):
   - 참여율 = 제출한 멤버 수 / 발행 때 멤버 수 (마스코트 제외)
   - 공들인 정도 = 아래를 각각 0~1로 맞춘 뒤 평균: 글 길이(같은 틀의 중앙값 대비), 캡션 유무, 받은 반응·댓글(마스코트 제외), 제때 제출
   - 보상 = 0.7 × 참여율 + 0.3 × 공들인 정도 (시작값, 시뮬레이션·데이터로 조정)
3. **언제 기록하나**: 미션이 마감된 뒤 한 번(마감 전에는 참여가 덜 모였으므로). 주기 작업이 "마감됐는데 아직 보상을 안 매긴 미션"을 찾아 계산 → 틀별 통계에 더한다. 두 번 더하지 않게 표시(`rewarded_at`).
4. **Thompson Sampling (Beta 분포)**: 틀마다 α=1+보상합, β=1+(횟수−보상합). 매번 각 틀에서 Beta 값을 뽑아 가장 큰 틀 선택.
   - **처음 그룹(데이터 적음)**: 전체 그룹 평균을 약하게 섞어 시작(계층적 사전 분포).
   - **최소 탐색**: 어떤 틀도 확률이 일정 값(예: 5%) 아래로 떨어지지 않게.
   - **재현성**: 난수는 `seed(그룹, 날짜, 슬롯)` 로 만든다 → 같은 날 다시 돌려도 같은 결과(지금 원칙 유지).
5. **기록(나중 분석용)**: 고른 틀의 선택 확률(propensity)과 정책 이름을 미션에 저장 → 오프라인 평가(IPS) 가능.
6. **스위치와 실험**: `hawe.mission.bandit.enabled=false`(기본). 켜면 그룹을 해시로 밴딧/기존 두 군으로 나눈다(비율 설정). 끄면 지금과 완전히 같은 결과(지문 테스트 그대로 통과).

## Edge Cases

- 새 그룹(기록 없음), 멤버 1명 그룹, 잠깐 쉬는 그룹(참여 0이 이어짐 — 틀 탓이 아님).
- 틀을 설정에서 빼거나 추가(빠진 틀 통계는 무시, 새 틀은 사전 분포로 시작).
- 하루 미션 여러 개(같은 날 같은 틀 금지 유지).
- 한 매체에 틀이 하나뿐(그림) → 밴딧이 고를 게 없으니 그대로.
- 개발자 모드로 시간을 옮겨 마감을 당긴 미션(개발 데이터는 실험에서 제외할지 결정).

## Constraints

- 스위치가 꺼져 있으면 지금과 완전히 같아야 한다.
- 같은 날 다시 계산해도 같은 틀(시드 고정).
- 마스코트 반응·댓글은 보상에 넣지 않는다.
- 외부 AI 호출 없음.

## Regression Risks

- 틀이 한쪽으로 쏠려 미션이 단조로워짐 → 최소 탐색 비율, 리포트로 감시.
- 데이터가 적으면 학습이 느림 → 사전 분포, 실험 기간 충분히.
- 보상 정의가 "쉬운 틀"만 좋게 볼 수 있음(참여율만 보면 쉬운 틀이 이김) → 공들인 정도를 섞은 이유. 가중치는 시뮬레이션과 실제 데이터로 점검.
